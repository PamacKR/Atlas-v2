# Open Product Questions

Carried over from `prd.md`'s "Open Product Questions" section, plus decisions made since. When a question is resolved, keep it here with its answer and status rather than deleting it — this is the changelog of product decisions, not just a todo list.

## 1. Notes format

- Should notes support Markdown, rich text, or both?
- Should handwritten annotations be possible directly within the app (vs. only imported)?

**Status:** Resolved (2026-07-25) — Markdown, typed notes only for now (handwritten/OCR notes are Phase 2, `ROADMAP.md`). Decided against rich text: the user's stated Notion workflow (write notes → export to PDF → paste into an AI chat) goes away entirely once Claude Code can query notes directly via MCP, and markdown is what Claude reads most naturally — rich text would just get flattened to something markdown-like anyway. Markdown also means no rich-text editor to build/maintain and notes stay trivially indexable by the existing FTS5 `search_index` table. Edited live via a WYSIWYG-style markdown editor (Milkdown/`@milkdown/crepe`, bundled — see `ARCHITECTURE.md` §8 "Notes"; Toast UI Editor was tried first and replaced after real gaps surfaced — no live list/heading shortcuts, no toolbar active-state feedback), not a raw markdown/preview split, so the day-to-day feel is still close to Notion. Organization is flat per course (no folders/subfolders) — the user's Notion structure was really "semester > course > session-titled note" (e.g. "W1L1"), and Atlas already provides the semester/course layers, so a note is just titled by the user (W1L1, W1L2, ...) rather than manually filed into a nested tree.

## 2. Synchronization

- How frequently should Classroom and Drive sync?
- Should synchronization be manual, automatic, or configurable?

**Status:** Resolved/built — Drive and Classroom each use the user-configurable per-source schedule delivered in Settings (Off / On launch only / Every N minutes where applicable), with explicit per-source and global sync actions. Classroom's default remains launch-only; Drive's default preserves its short automatic interval. Gmail is explicitly out of scope for Atlas as of 2026-07-29, so it is not an unresolved sync question.

**Implemented (2026-07-28).** The answer to "manual, automatic, or configurable" is **configurable, per source**. The Settings sync surface makes each active source's schedule and last-sync state visible, so a broken sync does not look identical to "nothing new":

- A **Sync section in Settings**, one row per active source (Drive / Classroom): **Off / On launch only / Every N minutes**, chosen from a small set of sensible intervals rather than a free-text field.
- A **"last synced" timestamp** per source, in plain relative language ("2 minutes ago"), plus the last error if the most recent attempt failed — so a broken sync looks broken instead of looking identical to "nothing new."
- A per-source **"Sync now"**, plus one "Sync everything."
- **Defaults exactly preserve today's behavior** (Drive 20s, Classroom launch-only), so nothing changes for the user unless they change it.

This supersedes the per-adapter, hardcoded-and-undocumented approach; the existing `setInterval` in `main.ts` becomes driven by the stored setting. The historical Gmail discussion below is superseded: Gmail is not an Atlas source.

**Status: Resolved/built (2026-07-28), Phase 3 item 2 of 3 (after conflict handling, #3).**

- **Storage**: one `app_settings` string per source (`sync_config_drive`/`sync_config_classroom`), either `'off'`, `'launch'`, or `'interval:<seconds>'` — deliberately one combined value rather than a separate mode+interval pair, so the Settings `<select>`'s own `value` attribute is exactly what gets stored, no translation layer. Unset (a fresh install, or before this shipped) falls back to defaults that reproduce the exact prior hardcoded behavior: Drive `interval:20`, Classroom `launch`.
- **`applySyncSchedule(source)`** (`main.ts`) replaces the old unconditional `setInterval(..., 20_000)`/one-shot launch call — it clears any existing timer for that source, then (unless the mode is `'off'`) runs one sync immediately and, for `'interval'` mode, starts a new recurring timer at the configured period. Called once per source at launch, and again immediately whenever the user changes that source's Settings dropdown, so a change takes effect without a relaunch.
- **`'off'` means no automatic sync at all, including at launch** — but a user's explicit action (Connect, setting the Drive folder, "Sync now") still runs regardless of the setting, since those are deliberate actions, not the background schedule this setting controls.
- **Visible status, not just a schedule**: `sync_<source>_last_success`/`sync_<source>_last_error` are recorded on every sync attempt (automatic or manual) and shown in Settings as a relative-time line ("Last synced: 2m ago") plus any error inline. A partial Classroom failure (some courses synced, others didn't) still advances `last_success` — the sync did run and did do useful work — but keeps the error text visible alongside it, rather than treating "mostly worked" as either a clean success or a clean failure.
- **UI**: a new "Sync" section in Settings > Sources, above the existing Drive/Classroom connection sections — one row per source (a `<select>` for the schedule + a "Sync now" button) plus a "Sync everything now" button. Reused the existing `.settings-row`/`.settings-row-label`/`.settings-row-hint` classes already established for the General tab's Theme/Accent rows, rather than inventing new ones — kept new elements visually consistent with the rest of Settings on the first pass, rather than repeating the earlier unstyled-button mistake (see #26's UI-consistency note).
- **Consolidated, not duplicated**: Classroom previously had its own standalone "Sync now" button (with a `classroom:syncNow` IPC handler and an `alert()` popup on per-course errors) living only in the Classroom section. Removed entirely in favor of the new unified per-source "Sync now" in the Sync section — two different-looking sync-now controls for the same source would have been exactly the kind of inconsistency the user has flagged before. The old `alert()` popup is also gone, superseded by the always-visible inline last-error text, which is less intrusive and doesn't require a click to dismiss.
- Verified with `npm run build` and a full `npm run verify` pass (no regressions) — worth the full suite since this changes real scheduling/timer behavior across both existing sync sources, not just a UI surface.

## 3. Offline behavior

- Which features should remain fully functional without an internet connection?
- How should synchronization conflicts be handled after reconnecting?

**Status:** Partially resolved by the architecture decision to use embedded SQLite (`ARCHITECTURE.md` §2) — everything in the canonical database (viewing, notes, search, manual uploads) works fully offline by construction.

**Conflict policy decided (2026-07-28), to be built as the next piece of work — and it turns out this isn't hypothetical, it's an active data-loss bug.** Found while planning the rest of Phase 3: `deadlines:update`/the deadline editor let the user edit *any* deadline including Classroom-synced ones, while `upsertDeadline` in `googleClassroom.ts` does `DO UPDATE SET title = excluded.title, due_at = excluded.due_at` on every sync. So editing a Classroom-sourced deadline (e.g. correcting a due date the professor changed verbally in class) is silently reverted on the next launch, with no warning and no trace. Same shape applies to `assignments` (title/description/due_at). `deadlines.completed` is already safe — the upsert never touches it.

Decided approach, confirmed with the user:

- **Per-field protection, not whole-row locking.** Atlas records which specific fields the user edited by hand and never overwrites those on a re-sync, while still accepting source updates to fields they didn't touch. The user explicitly chose this over the simpler "once edited, this row stops syncing entirely": a moved deadline is precisely the update you least want to miss, so one cosmetic title edit must not permanently blind the row to real due-date changes.
- **Locally-edited state must be visible, not invisible.** A marker on any deadline carrying local overrides, plus a "reset to the Classroom version" action to discard them — otherwise the user has no way to tell why a deadline stopped matching Classroom, or to undo it.
- **Deleted-at-source items are greyed out, not deleted.** Today nothing ever removes a `deadlines`/`assignments` row whose Classroom coursework was deleted at the source — there's no reconciliation pass at all (unlike `drive_pending_files`, which does reconcile). Rather than hard-deleting on disappearance, mark it as no longer present in Classroom and let the user dismiss it: the user chose this because a hard delete could destroy notes, descriptions, or `@`-mentions they had attached to that deadline.

**Status: Resolved/built (2026-07-28).**

- **Schema**: `deadlines` gained `local_overrides` (comma-delimited field names, e.g. `"title,due_at"` — deliberately plain delimited text rather than JSON, to avoid depending on SQLite's JSON1 extension being present in this `better-sqlite3` build; the two possible tokens never collide as substrings), `classroom_title`/`classroom_due_at` (Classroom's current values, updated by every sync regardless of overrides — this is what makes "reset" instant and offline, with no fresh API call needed), and `classroom_removed`. `assignments` gained `classroom_removed` too (display-only — assignments has no direct editing UI; the user always edits the mirrored `deadlines` row instead, confirmed by checking `openAssignmentDetail` in `renderer.ts`, which routes an assignment click to its linked deadline).
- **`deadlines:update` (`main.ts`)** now diffs the incoming title/due_at against the stored values *before* writing, and only for a Classroom-linked deadline (`classroom_coursework_id IS NOT NULL` — a manually-created deadline has nothing to protect against): whichever of the two actually changed gets added to `local_overrides` (union with whatever was already there, never cleared as a side effect of an edit).
- **`upsertDeadline` (`googleClassroom.ts`)** now uses a `CASE WHEN instr(...) THEN <existing value> ELSE excluded.<value> END` per protected field, checked against `local_overrides`, instead of unconditionally overwriting — verified directly against a real SQLite database (not assumed) that this correctly preserves an overridden field while still applying a sync update to the field the user didn't touch, in the same upsert.
- **`deadlines:resetClassroomOverrides`** — a new handler, purely local (copies `classroom_title`/`classroom_due_at` back into `title`/`due_at` and clears `local_overrides`), so it works offline and needs no live Classroom call. Wired to a "Reset to Classroom version" button shown in the deadline viewer whenever `local_overrides` is non-empty, alongside plain-language text naming which fields were overridden.
- **Reconciliation** (`syncClassroomCourseworkForMappedCourses`) now computes the live courseWork ID set per course on every sync and marks any `deadlines`/`assignments` row whose `classroom_coursework_id` has disappeared as `classroom_removed = 1` (cleared back to 0 if it ever reappears) — the gap this closes: previously nothing ever reconciled deleted coursework at all, unlike Drive's `drive_pending_files`, which already did.
- **UI**: a `classroom-removed` CSS class (opacity, no strikethrough — this isn't "done," it's "no longer tracked upstream") plus a small badge in both Deadline list views, and a notice in the deadline viewer ("This assignment is no longer in Google Classroom. Delete it here if you want to remove it.") — the user's existing right-click Delete is the dismiss action, no new plumbing needed for that part.
- **Dashboard exclusion**: `dashboard:stats`/`dashboard:upcomingDeadlines` now also filter `classroom_removed = 0`, alongside the existing `stale_import = 0` — planning around a deadline that's been deleted at the source would be actively misleading, unlike a merely-old `stale_import` row. The full Calendar page (`deadlines:listAllWithCourse`) intentionally keeps no such filter, same reasoning as `stale_import`.
- **A second real bug found and fixed in the same pass**: `assignments.posted_at` (added earlier this session for #26) had been added to `database.ts`'s migration but never to `schema.sql`'s fresh-install `CREATE TABLE`, so a brand-new install would be missing the column entirely until the app happened to run the migration path. Fixed by adding it to `schema.sql` too, alongside the new `classroom_removed` column.
- Verified the core per-field-protection logic directly against a real (in-memory) SQLite database before trusting it, not just by reading the SQL — confirmed an overridden field survives a re-sync while an untouched field still updates, and that a Classroom title/due-date change is correctly shadowed into `classroom_title`/`classroom_due_at` even while the user-facing field stays protected. Full `npm run verify` also passed with no regressions.

**Follow-up (2026-07-28, later the same day) — the user reported "Reset to Classroom version" as buggy.** Built a scripted end-to-end reproduction (real Electron app via Playwright, a simulated Classroom-linked deadline via direct DB writes since a live OAuth token can't be scripted) rather than guessing from a description. Findings:

- **The reset mechanism itself was never actually broken** — the scripted repro confirmed the database update, the reopened viewer, and the deadline list all correctly reflect a reset immediately, with no stale state anywhere.
- **The real cause of the confusing experience: saving an edit closed the entire deadline window with no visible confirmation at all** — no new date, no "you've edited this" marker, nothing — until the user reopened the deadline by hand. This was pre-existing behavior (not introduced by this feature) that made "I clicked reset and nothing happened" an easy conclusion to reach, since whatever was on screen right after saving was already stale or gone. **Fixed**: saving now reopens the viewer showing the saved result directly, so the new value and the edited/removed markers are visible immediately, no extra click needed.
- **Second ask, in the same follow-up: make an edited deadline visible without opening it at all.** A `.deadline-edited-badge` ("✎ Edited") now shows directly in every place a deadline is listed — the course-detail list and icon views, the Dashboard's Upcoming widget, and the Calendar's upcoming sidebar list — with a compact "✎" prefix used in the Calendar's month-grid chips instead (too small for a full text badge). Shared via one `makeDeadlineEditedBadge()` helper so all five surfaces stay consistent rather than reimplementing the same check five times.
- Verified via a second scripted repro asserting the badge appears in the list *without clicking in*, disappears immediately after a real reset, and appears in both the course-detail list and the Dashboard widget simultaneously (confirmed these are two separate DOM nodes for the same deadline, not a duplicate-rendering bug). `scripts/verify-app.js` updated to close the deadline viewer explicitly after each save (six sites), since it no longer closes itself — full suite passes.

**Second follow-up (2026-07-28, same day, immediately after the above) — the Calendar page specifically still doesn't refresh, root cause confirmed but NOT YET FIXED.** The user reported that after editing a deadline's due date (or resetting it) *from the Calendar page*, the Calendar itself never reflects the change — the deadline appears to stay at its old date until the user changes month and back, which forces a fresh re-render.

- **Root cause, confirmed by reading the code, not guessed**: opening a deadline from anywhere (`openDashboardDeadline()` in `renderer.ts`) calls `selectCourse(course)`, but `selectCourse()`/`showCourseDetailView()` only toggle the *internal* sub-view of the Courses page (`#courses-list-view` vs `#courses-detail-view`) — neither one calls `showPage('courses')` or changes the module-level `currentPage` variable. This is consistent with the app's own documented overlay design ("a global overlay... opening one never navigates away from whatever page is currently showing, just layers on top" — see the note above `openNoteEditor`/`openPreview`). So if the user opens a deadline while looking at the **Calendar** page, `currentPage` stays `'calendar'` the entire time the deadline viewer is open, and the Calendar page's own DOM (still the actual visible background, once the modal closes) is never touched.
- **Why the fixes so far didn't catch this**: `resetCurrentDeadlineOverrides()` and the deadline edit-save submit handler both refresh `renderDeadlines()` (course-detail scoped — harmless no-op here since that view isn't visible) and `renderDashboard()` (this *does* work correctly when the deadline was opened from the Dashboard, which is why the Dashboard Upcoming widget already updates live and the badge-verification scripted test — which used the course-detail flow — passed clean). **Neither checks `currentPage === 'calendar'` and calls `renderCalendarPage()`**, which is the one additional call needed.
- **Exact fix for next session**: in both `resetCurrentDeadlineOverrides()` and the `deadlineEditForm` submit handler (`renderer.ts`), alongside the existing `renderDeadlines()`/`renderDashboard()` calls, add `if (currentPage === 'calendar') await renderCalendarPage();`. Worth auditing the same gap in `makeDeadlineCheckbox()`'s completion-toggle handler and the deadline-delete handler too, for full consistency — any deadline mutation while Calendar is the visible background page should refresh it, not just edit/reset.
- **User also reiterated "no confirmation"** for the reset action specifically (separate from the edited-badge/reopened-viewer fixes already shipped) — worth deciding, next session, whether the reopened viewer + badge are sufficient confirmation or whether an explicit "Reset" status message (matching the pattern already used for sync status text) is still wanted once the Calendar refresh gap above is closed, since a lot of the "no confirmation" feeling may simply have been the Calendar-refresh bug itself.
- **Status: FIXED (2026-07-28).** The fix went into `renderDeadlines()` rather than into each caller: that function is already the shared refresh point every deadline mutation calls (save, reset, delete, completion toggle) and already refreshed Dashboard, so adding `if (currentPage === 'calendar') void renderCalendarPage();` next to the existing `renderDashboard()` call covers all four paths at once instead of patching each separately. `npm run build` and the full `npm run verify` suite both pass.

## 4. Course lifecycle

- How are semesters archived?
- Should old courses remain searchable by default?

**Status:** Resolved/built (2026-07-28). A course can now be archived (right-click a course card, or a button on its own detail page) without deleting anything — every file, note, and deadline stays exactly as it was. Archiving only does three things: the course drops out of the normal Courses grid (a "Show archived courses" toggle switches to viewing archived-only, never mixed with active ones), it's skipped by the Ashoka Planner/Classroom-mapping name-match suggestions, and Classroom stops auto-syncing new content into it. **Archived courses stay fully searchable** (global search was never filtered by archived status to begin with) — the point of archiving is decluttering the course list, not making last semester's material harder to find. Unarchiving undoes all three instantly, including picking Classroom sync back up with no need to reconnect anything. Delete remains a completely separate, destructive action — archiving is not a replacement for it.

## 5. AI provider independence

- Should the data structures and documentation remain generic enough to support any AI coding agent/reasoning engine, without redesigning the platform per tool?

**Status:** Yes, by design — and formalized further on 2026-07-27 (see the dated entry below): the project's own operating instructions moved from `CLAUDE.md` to a tool-agnostic `AGENTS.md`. The Context Builder (`ARCHITECTURE.md` §5) and canonical schema are already agent-agnostic; the MCP server (`ARCHITECTURE.md` §6) is one transport on top of them — MCP itself is a vendor-neutral protocol, not tied to any single client — and the static file-export fallback exists specifically so non-MCP AI tools aren't locked out. Course AI profiles (PRD §19) are the one place per-agent tuning lives, and even those are just structured preference data Atlas supplies to whatever reasoning engine is in use — not tool-specific logic.

## New questions raised while documenting the architecture

### 6. Data directory layout

Where do original files (scans, PDFs, uploads) live on disk relative to the SQLite database and app config?

**Status:** Resolved (updated 2026-07-23) — `Downloads/Atlas-Storage/` is the managed data folder (course subfolders inside it), chosen over a hidden app-data location so the user can easily browse/add/remove files by hand. ### 7. Google API credential handling

Classroom/Gmail/Drive all need Google Cloud credentials. Does the user bring their own Google Cloud project (OAuth client), or does Atlas ship with one baked in?

**Status:** Resolved — bring-your-own Google Cloud OAuth client, on the free tier, with no billing account attached (per the zero-API-fees constraint in `ARCHITECTURE.md` §0). OCR no longer needs a Google credential at all, since it moved to local Tesseract.js (`ARCHITECTURE.md` §3).

### 8. College Google Workspace access — real risk, not yet verified

The user's primary account for Classroom/Gmail is a **college Google Workspace for Education account**, not their personal Google account. Workspace admins commonly restrict which third-party/custom OAuth apps can access Classroom, Gmail, or Drive API scopes for accounts on the domain — independent of cost, this can block API access outright regardless of what Atlas builds.

**Status:** Resolved (verified 2026-07-23) — tested directly via Google's OAuth 2.0 Playground, signed into the college account, requesting both Classroom read/write scopes and `gmail.readonly`. Both completed with a normal `HTTP 302` redirect and authorization code — no `admin_policy_enforced` or app-blocked error, which is what a Workspace admin restriction would produce. The college domain allows third-party OAuth apps to access Classroom and Gmail API scopes. Phase 3 (Classroom/Gmail sync) can be scoped against the college account without a fallback plan for this specific risk.

Caveat: this confirms *consent* succeeds, not that every specific scope Atlas will eventually need is unrestricted (e.g. write scopes, or Drive scopes, weren't all exhaustively tested) — worth a quick recheck if Phase 3 scoping turns up a scope not covered by this test.

### 11. Folder→course mapping for local folder watching

When Atlas watches a local folder for new files, how does it know which course a detected file belongs to — explicit user-configured mapping, or auto-guessing from file content/name/location?

**Status:** Resolved (2026-07-25) — explicit only. The user maps a folder to a specific course when adding it (native folder picker, from that course's "Watched folders" section); there is no auto-guessing. Reasoning: guessing which course a file belongs to from its content or name would be Atlas making an inference about academic meaning, which cuts against the "Atlas owns data, Claude owns reasoning" rule (`CLAUDE.md`) — that kind of association-with-uncertainty belongs to a human decision (or later, an explicit Claude Code query), not a silent sync-adapter heuristic. See `ARCHITECTURE.md` §4.

### 12. PPTX fidelity — revisit the Google Drive route once Phase 3 (sync) is underway

The user tried "Open in browser" on a real PPTX and, while accepting the current text-only outline as fine *for now*, was explicit that the fidelity isn't great and they'd like to revisit routing PPTX (and possibly DOCX/XLSX) through Google Drive/Docs/Slides for real layout rendering — the option scoped out of the "Open in browser" work (session 20) specifically because it requires uploading files to Google Drive, a Phase 3-scale change.

**Status:** Resolved/built (2026-07-28). Phase 3's Drive integration was underway by the time this was revisited, exactly as anticipated above. Initially pushed back on (see the dated discussion below) on the assumption that files leaving the user's machine was undesirable and that a local desktop-app fallback existed — both assumptions were wrong once checked directly with the user, so the recommendation reversed.

- **What was built**: an "Open in Google Drive" action (resource right-click menu, and a button in the in-app preview modal) for `.pptx`/`.docx`/`.xlsx` resources only — PDFs/images already render natively and don't need it. The file is uploaded to a dedicated "Atlas Previews" folder Atlas creates and manages in the user's Drive, then Drive's own viewer opens in the browser — real slide/document layout, not a conversion to Google Slides/Docs/Sheets (converting would introduce its own fidelity loss; Drive can preview the original Office format directly).
- **Upload is cached, not repeated.** A resource's Drive copy is remembered (`resources.drive_preview_file_id` + the local file's size/mtime at upload time); a later open with the same size/mtime reuses the existing Drive file instead of re-uploading, so only the first open of a given file is slow. A changed file gets re-uploaded in place (same Drive file ID, not a second copy).
- **The existing local preview is untouched and stays the default** — this is an additional action, not a replacement, so offline viewing and the instant local outline both still work exactly as before.
- **Why the original pushback was wrong, on reflection**: the user was never opposed to files leaving the machine if it meant a better viewing experience, has no Word/PowerPoint installed (so "open in the desktop app instead" wasn't a real alternative), and pointed out that *some* fidelity improvement over a text-only outline is a very low bar to clear. All three corrected real, unverified assumptions behind the original recommendation to leave this deferred indefinitely.
- **Scope note**: only `.pptx`/`.docx`/`.xlsx` (Office Open XML) are supported — legacy `.ppt`/`.doc`/`.xls` were out of scope for this pass (Atlas's kind-detection may not even categorize those correctly today; flagged as a possible follow-up, not addressed here).
- See `ARCHITECTURE.md` §7 for the full implementation writeup, including the multi-Google-account caveat (Drive uses the personal account, Classroom the college one) worth being aware of.

**Follow-up, same day, after the user's first real test:**
- **Real bug found: the seeded test `lecture-slides.pptx` files weren't valid PowerPoint files.** They only contained two bare slide-text XML fragments with none of the surrounding package structure a real `.pptx` needs (manifest, relationships, an actual presentation part) — Atlas's own local preview never noticed because it just regexes for text inside slide XML directly, but Google's real importer correctly refused with `UNSUPPORTED_CONVERSION: ... missing the main document/presentation/workbook part`. Not a bug in the new feature — confirmed by inspecting the file's internal structure directly, not guessed. The user asked for the 5 placeholder files to be fixed rather than left broken; regenerated as genuinely valid minimal `.pptx` packages (same slide text preserved) via a one-off script, same pattern as how this test data was originally created (`STATUS.md` session 44).
- **Uploads now land in a per-course subfolder inside "Atlas Previews"**, not flat in one folder — the user asked whether this was worth doing even though they mostly interact through the app rather than Drive directly. Worth doing regardless: several courses' files sharing an identical filename (exactly the case with the seeded `lecture-slides.pptx` files above) would otherwise be indistinguishable from each other in a flat folder. See `ARCHITECTURE.md` §7.
- **Real UI bug**: the new "Clear Drive preview cache" Settings button had no styling at all (Atlas styles Settings buttons individually by ID in `styles.css`, not via a shared class, and the new button's ID was never added to that rule) — rendered as an unstyled native browser button next to properly-themed ones. Fixed by adding it to the existing shared selector.

### 13. Deadlines vs. Assignments — one overlapping manual-entry UI, or two?

The schema has two separate tables that both cover "things with a due date": `deadlines` (PRD §12's unified academic timeline — assignments/readings/quizzes/labs/projects/exams/manual tasks, one list per course) and `assignments` (a would-be separate course tab per PRD §8, carrying a description and a submission-status field — open/submitted/graded — that only really makes sense once Google Classroom sync exists to populate it). With no sync built yet, a user manually adding "Homework 3, due Friday" could plausibly go in either one.

**Status:** Resolved (2026-07-26) — build Deadlines only for Phase 1. Asked the user directly, given the real overlap; they chose the unified Deadlines list, deferring a separate Assignments tab to Phase 3. Reasoning: `deadlines.kind` already includes `'assignment'` as one of its values, so a manually-tracked assignment due date is already representable there — building a second, parallel UI for it now would just be busywork with no real difference until Classroom sync actually needs the `assignments` table's description/status fields for real synced data. Revisit once Phase 3 (external sync, `ROADMAP.md`) starts populating `assignments` from Classroom.

### 14. Multiple scrollbars visible at once in some views

**2026-08-03 update:** the Atlas-owned in-app PDF preview no longer embeds Chromium's PDF viewer, so its preview scrollbar is now part of Atlas and receives the global rounded styling. This question remains open only for scrollbars in external browser windows, which Atlas cannot style.

### 16. Auto-categorizing an uploaded file into the right course

The user asked: if a file is just uploaded somewhere generic, can Atlas figure out which course it belongs to on its own?

**Feasibility:** Depends heavily on what "figure out" means, and this one runs straight into the "Atlas owns data, the AI agent owns reasoning" rule (`AGENTS.md`) plus the no-AI-in-Atlas guardrail — worth being precise about what's actually allowed:

- **Not feasible as "silently, always correct, no confirmation"** — that would require Atlas itself to semantically understand file content and match it to a course, which is exactly the kind of AI-inference-written-back-as-fact `AGENTS.md` prohibits (mirrors the reasoning already settled in question #11 for folder watching — explicit mapping only, no silent guessing).
- **Feasible as a local, rule-based *suggestion*, confirmed by the user before it's saved.** Atlas already extracts text from every resource kind it can preview (markdown/DOCX/XLSX render as text/HTML today; PDF/image would need OCR, which is Phase 2 territory). A plain keyword/regex match — course code appearing in the filename or file text, course name appearing in the file text — against the list of existing Atlas courses is cheap, local, deterministic, and not an AI call at all. The existing course-picker modal (`#course-picker-overlay`) could simply pre-select/highlight its best guess instead of defaulting to nothing, with the user still clicking to confirm (or picking a different course) — same UI, smarter default.
- **A step further (genuinely "smart," not just keyword matching)** — e.g. reading and understanding an ambiguous file's actual subject matter — is the connected AI agent's job at runtime (via MCP, per the core architectural rule), not something to build into Atlas's own process. That would look like: the user asks their AI agent "where does this file go," it reads the file and Atlas's course list via the Context Builder, suggests a course, and *the user* confirms the move through Atlas — never an automatic background classification.

**Status:** Open — the rule-based "suggest, don't auto-assign" version is buildable now and doesn't need a phase change; the "ask an AI agent to help sort an ambiguous file" version depends on Phase 4 (Context Builder/MCP) already existing. Needs a decision on whether the rule-based version is worth building before then, or whether manual course selection at upload (already fast — one modal click) is good enough until Phase 4.

### 21. Classroom sync reliability bug, per-course Connect button, Classwork tab, Drive-link attachments, and Calendar

Built 2026-07-27, in direct response to a real bug report: the user's last Classroom import ("before we integrated the Ashoka Planner") pulled zero content for any mapped course.

- **Root cause, corrected after a real "Connect to Classroom" test still failed (2026-07-27, later the same day)**: the first pass fixed a real problem (no per-course `try`/`catch` around the sync loop) but that wasn't actually what was breaking things. The true cause: `upsertAssignment`/`upsertDeadline`/`upsertAnnouncement`'s `db.prepare()` calls threw `"ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint"` **unconditionally, every single time** — before the per-course loop even started. Their `ON CONFLICT (col) DO UPDATE SET ... WHERE col IS NOT NULL` syntax put the partial index's `WHERE` predicate after `DO UPDATE SET` (that's a *result-filter* clause, a different thing), but SQLite requires a partial unique index's predicate to be restated immediately after the conflict column list (`ON CONFLICT(col) WHERE col IS NOT NULL DO UPDATE SET ...`) before it will recognize the index as a valid conflict target. Confirmed by preparing both versions of the statement directly against the user's real `atlas.db` via a one-off `ELECTRON_RUN_AS_NODE=1` script. This means the original "nothing carried over" bug was likely never about a missing try/catch at all — these three statements probably never once succeeded since the Classroom adapter was first built. Fixed by moving the `WHERE` clause to directly follow the conflict target column list on all three.
- The per-course `try`/`catch` around `courseWork`/`announcements`/`courseWorkMaterials` calls is still a real, worthwhile fix (kept from the first pass) — failures are collected as `{courseId, courseName, message}` and returned up through `scanClassroomAndNotify`/`classroom:syncNow`/both mapping handlers/the new per-course connect handler, and the renderer `alert()`s the user when a sync partially fails instead of it looking identical to success.
- **A third real bug in the same live-test round, found immediately after the SQL fix**: connecting a course now got past the SQL error but failed with `"Request had insufficient authentication scopes."` — `courseWorkMaterials.list` (added for the Classwork tab, this same session) needs `classroom.courseworkmaterials.readonly`, a distinct scope with no `.me` variant, which was never added to `CLASSROOM_SCOPES` in `googleAuth.ts` when the Classwork sync was built. Fixed by adding it. **The user needs to disconnect and reconnect Google Classroom once** for this to take effect — an already-issued refresh token doesn't retroactively gain a newly-added scope; only a fresh OAuth consent grants it.
- **Gap the user caught while testing, before it caused real harm**: disconnecting a course from Classroom (per-course "Disconnect" button) only cleared `courses.classroom_course_id` — the already-synced announcements/assignments/deadlines/classwork/link-resources stayed untouched. That means connecting the *wrong* Classroom class had no real undo: disconnecting wouldn't remove the wrongly-imported content. **Resolved (user's explicit choice)**: per-course Disconnect now deletes everything that came from that link for that course — `deadlines`/`assignments` (`source='classroom'`), `announcements` (`source='classroom'`), all of that course's `classwork_materials` rows (cascades any resources referencing them via `classwork_material_id`), and any remaining `resources` with `source='classroom'` — all in one `db.transaction()`. The renderer confirms with the user first (`showConfirm`, same pattern as course deletion) since this is destructive and irreversible. The Dashboard's global "Disconnect Google Classroom" (revoking the whole OAuth connection) is unchanged — it still only clears the stored token, since it doesn't target one specific course's mapping the way the per-course button does.
- **Attachments redesigned as Drive links, not downloads** (user's explicit preference — "drive might be better for me as that means less files on my laptop"): a new `resources.kind = 'link'` value holds the external URL directly in `file_path` (no download, no dependency on Drive also being connected). This *also* fixes the old "link/YouTube/Forms materials have nothing downloadable" gap noted in question #20 — a link-kind resource represents any of those uniformly, since none of them need a local file. Opening one calls `shell.openExternal` instead of routing through the local preview server.
- **Classwork (the ungraded courseWorkMaterials tab)**: new `classwork_materials` table, synced the same per-course-guarded way as courseWork/announcements. Its attachments land as `kind='link'` resources with `classwork_material_id` set, so the Classwork course-detail section can group "post + its links" the way Classroom's own tab does.
- **Per-course "Connect to Classroom" button**: course detail now has its own Connect/Disconnect control (`classroom:listAvailableCoursesForLinking` + a small picker overlay) — this is the workflow the user actually wanted (question raised 2026-07-26): pre-create next semester's courses via the Ashoka Planner import, then link each one to Classroom directly, rather than mapping via the discover-new-courses review panel (which only ever offers "map to existing" for courses Atlas already knows about, or "create new").
- **Course-detail Announcements/Assignments/Classwork**: three new inline sections (same visual idiom as the existing Deadlines/Watched-folders sections — course detail had no tab pattern *at the time this was built*; that changed later the same session, see question #22), shown only once a course is actually linked.
- **Dashboard "Upcoming" widget and full Calendar page**: built from two screenshots the user shared. The Dashboard widget got a kind-filter tab row (All/Assignments/Exams/Readings/Other) and a denser row layout (date block, course-colored left border, kind badge, relative due-in label). The Calendar page (new sidebar entry) is a v1 scope only: month grid with up to 3 deadline chips per day + "+N more", and a right-column grouped-by-date Upcoming list + course-color legend. **Deliberately not built yet** (fast-follows, not silent cuts): a Day/Week view toggle, a mini date-picker, and the per-kind/per-course "Filters" checkbox panel the screenshot also showed.

**Status:** Resolved/built. Same manual-verification limitation as question #20 (no live-account coverage in `scripts/verify-app.js`) — verified by rebuilding and a spot pass against the user's 5 real Ashoka-imported courses, not by an automated Classroom-connected test.

### 26. Classroom files falsely reported as "changed today" on every launch, notes falsely marked changed on open/close, and the "View full calendar" grey space

Raised 2026-07-28. The user noticed the Dashboard's "What changed today"/"Recently added" widgets listed every single Classroom-synced file as new on every app launch, at exactly the time the app was opened — and separately, that simply opening and closing a note (no edit at all) also made it show up as "changed." Both turned out to be real, root-caused bugs, not vague flakiness.

- **Real bug (Classroom files)**: `reconcileCourseStorage()` — the function that removes a resource's database row when its file has been deleted by hand from a course's storage folder — checked every resource in a course, including Classroom attachments (`kind = 'link'`), whose "file" is actually just a saved web address, not a real file on disk. Checking "does this file still exist on disk" for a web address always came back "no," so the function deleted every single Classroom-linked file on every launch — and moments later, the regular Classroom sync recreated them all, stamped with that exact moment as their "added" time. That's why the Dashboard showed every Classroom file as brand new, every time, at launch time. Fixed by excluding link-type resources from that disk check entirely, since they were never something that check was meant to cover. A related latent gap — the database had no rule actually preventing a Classroom file from being saved twice — was fixed at the same time, and the ~155 already-affected resources had their added dates repaired using Classroom's own real posting timestamps (a one-time, automatic cleanup on next launch), not guessed or left wrong.
- **Real bug (notes)**: opening a note primes the editor, which fires its own "content changed" signal once during setup even when the user hasn't typed anything — and closing a note always saved regardless, with no check for whether anything had actually changed. Both are now guarded: opening or closing a note with no real edit no longer touches its last-modified time or search index, in both the editor and the underlying save handler (two layers, so any future save path gets the same protection automatically).
- **Cosmetic bug ("View full calendar" grey space)**: the button sat directly under the deadline list rather than anchored to the bottom of its box, so when the list was short there was visible empty space between the list and the button, then more space below the button too. Fixed by pinning the button to the bottom of its box directly — the same fix already proven on the Courses page's card layout (#25) — so any empty space now sits between the list and the button (where it reads as normal breathing room) instead of below the button.

**Status:** Resolved/built. Verified via `npm run build`; the Classroom-related fixes can't be exercised by `scripts/verify-app.js` (needs a live Classroom account, same limitation as #20–#22) — confirm against the user's real launch that Classroom files stop getting fresh "added" dates on repeat launches.

### 27. Dashboard "View full calendar" gap, round 4 — the actual root cause this time

The #26 fix above (pinning the button to the bottom of its own box) only moved the gap from below the button to between the list and the button — the user reported it was still there, now sitting above the button instead. This is the same "dashboard height whack-a-mole" flagged as possibly recurring back in #25.

- **Actual root cause**: the Dashboard's three columns (My Courses | Upcoming | Recently-added/What-changed) are forced to the same height (`align-items: stretch`, the CSS Grid default) so their bottoms line up flush — a deliberate choice from an earlier session, matched to a reference screenshot. With real data, the right column (two stacked widgets, often 7-8 resource rows) is genuinely taller than the Upcoming widget's real content (the user currently has only 2 real upcoming deadlines). Stretch then forces the Upcoming widget up to match that height regardless — and the deadline list, which had `flex: 1`, dutifully grew to fill that extra space with nothing in it, since there's no more real data to show. No pixel value or button position was ever going to fix this: the box was being made taller than its content by design, for a reason (flush bottoms) that's fundamentally in tension with "never show blank space," and the earlier fixes were only ever moving the resulting gap around rather than removing its cause.
- **Fix**: `#dashboard-main-grid` now uses `align-items: start` instead of stretch, and `flex: 1` was removed from the My Courses/Upcoming list rules (`max-height` + `overflow-y: auto` stay, for the case a list genuinely has enough rows to need scrolling). Each column is now exactly as tall as its own real content, never artificially stretched to match a taller sibling.
- **Trade-off, stated plainly rather than discovered later**: the three columns' bottoms will no longer always line up flush when their content genuinely differs in length (e.g. 2 deadlines vs. 7 resources) — that flush-bottom look was the whole reason the previous approach existed. This is the direct trade against "no dead space when there's nothing to fill it with," and there's no way to have both when the underlying data itself is uneven. Revisit only if the user says the uneven bottoms look worse than the gap did.

**Status:** Resolved/built. Verified via `npm run build`; the visual result (uneven column bottoms vs. no blank space) needs a look against the user's own real Dashboard, not just the 1-course test fixture, same caveat as #24/#25.

### 28. Gmail adapter — scope, and why Phase 4 now comes before it

Planned 2026-07-28 while drafting the rest of Phase 3. The design discussion changed both what the Gmail adapter should be *and* the order of the remaining roadmap, so both are recorded here together.

**The user's actual motivation, in their words:** "the college spams us with so many emails there are many times you just miss something important." Plus two concrete cases Classroom doesn't cover — a venue change for an exam announced only by email, and a TF replying to a doubt they emailed about. They were explicit that whether course communication happens over Classroom or email "all depends on the professor," and that their semester hasn't started yet, so **none of this can be validated against real usage until it does**.

**The key architectural split, which resolves the user's own confusion ("is this something feasible within the app or something an AI agent should handle?"):**

> "Is this email important?" is not a fact about an email — it depends on the user, that week, what they're working on. Atlas storing a permanent `important` flag would be exactly the AI-inference-written-back-as-canonical-fact that `AGENTS.md` and PRD §17 prohibit, *and* it would be wrong much of the time. "Which emails exist, from whom, and what they say" **is** a fact, and that's Atlas's job.

So: Atlas captures and files email; an AI agent answers "what did I miss?" freshly at query time, via Phase 4's Context Builder/MCP layer. No importance judgment is built into Atlas at all.

**A point worth not underrating, raised during the discussion:** a user-curated tracked-sender list already solves most of the stated problem *with no AI whatsoever*. The user's difficulty isn't recognising an important email — they'd know a venue change mattered instantly — it's that it's buried under college noise. A feed restricted to the ~20 people who actually matter *is* the filter; the noise simply isn't in the room. An AI agent adds one specific thing on top: catching something important from a sender they hadn't thought to add. That's real, but it's the smaller half, and it's the half that genuinely needs Phase 4.

**Agreed scope for the Gmail adapter when it is built:**

- **A user-managed tracked-sender list** (Settings), each address optionally tied to a course. Course-tied senders file automatically; senders with no course (exam office, department) still come in, to a general non-course view. The user estimates ~20 addresses, but couldn't give a real number pre-semester. Atlas fetches from these addresses and nobody else — no domain-wide sweep in v1.
- **Automatic thread tracking**: any conversation containing a message the user sent is tracked, so a TF's reply arrives without the TF needing to be on the list first. Purely mechanical (thread contains a sent message), no content judgment. Bounded to the college domain and to threads from the connection date onward, so it can't sweep in personal mail history.
- **Offer-to-track**: an untracked sender appearing in a tracked thread prompts "track this person too?", so the list gets built through use rather than upfront data entry.
- **Full email bodies are stored and readable in-app** for everything Atlas fetches. An earlier draft proposed storing only metadata until an email was assigned to a course; the user asked directly whether that meant they couldn't read the email in the app, and the answer made the restriction indefensible for mail they'd explicitly opted into. Metadata-only was only ever intended for a broad "everything else from the college domain" bucket — **that bucket is dropped from v1 entirely** and revisited only if/when Phase 4 exists to triage it.
- **Attachments are added to a course manually, per attachment** (user's explicit choice, overriding the original auto-import proposal) — listed on the email with an "Add to course" action each. Simpler, and avoids courses filling with signature images.
- **A global Email page** (mirroring the existing Resources/Notes pages, with a course filter) plus a per-course Email tab — because not all tracked email is course-shaped, and a course-only surface would have nowhere to put exam-office or department mail.
- **Read-only Gmail access** (`gmail.readonly`). Atlas can never send, delete, or modify anything. Same restricted-scope 7-day testing-mode reconnect cycle as Drive/Classroom, and its own separate connection/token rather than being bolted onto Classroom's (which would force a Classroom reconnect and couple two independently-useful features).
- **No importance scoring, ranking, or filtering by content anywhere in Atlas.**

**Roadmap reorder: Phase 4 (Context Builder + MCP) now comes before the Gmail adapter.** Reasoning, agreed with the user:

- The user's primary want from Gmail ("tell me what I missed") is a Phase 4 capability by definition — it cannot be delivered by the Gmail adapter alone no matter how it's built.
- Phase 4 is still entirely unbuilt while being the product's actual purpose (PRD §16/§18/§21), and everything already in Atlas — courses, notes, deadlines, resources, Classroom assignments/announcements — is already worth querying. Phase 4 delivers value immediately, with or without email.
- Building Gmail's storage shape *before* knowing how the agent actually queries risks designing the wrong shape and reworking it.
- The user's response: "If you think doing phase 4 first will help better implement the gmail integration then im okay with that."

**Status:** Superseded 2026-07-29 — the user decided Gmail doesn't belong in Atlas at all, not just later in the roadmap. Everything above is kept as the accurate record of that day's design discussion, but none of it should be built here. If a Gmail-reading tool is ever wanted, it's a separate, standalone project (e.g. "reads out important emails"), unrelated to Atlas. See `ROADMAP.md`'s "Explicitly out of scope" section.

(Prior status, no longer current: "Agreed/planned, not built. Gmail is deferred until after Phase 4.")

### 29. Scanned Classroom PDFs can't be OCR'd — they have no local file to render

Found 2026-07-29 while measuring the results of the first full remote-attachment extraction pass against the user's real data.

**9 of the user's Classroom Drive attachments extracted as `empty`** — they parsed fine, but contain no text layer at all. These are scans (photographed or scanned readings), all in Development Economics. `empty` is exactly the signal that normally surfaces Atlas's existing "Run OCR" button.

**The problem:** that OCR flow (`ocr.ts`) renders pages from a **local file path** and OCRs the resulting images. A remote attachment deliberately has no local file — that's the entire point of `remote-attachment architecture` §3.2 ("nothing is ever written to `Atlas-Storage/files/`"). So the one recovery path Atlas has for a scanned document is structurally unavailable for exactly the files most likely to need it.

Right now these 9 files are permanently unreadable to the AI agent: not a failure, not retryable, just silently empty.

**Options:**

- **(a) Temp-fetch for OCR.** Re-fetch the file to the OS temp directory (the same mechanism `remoteFetch.ts` already uses for large PDFs), run the existing OCR pipeline against it, store the accepted text as `origin='ocr'` parts, delete the temp file. Consistent with the existing no-local-download guarantee, which is about `Atlas-Storage/files/` specifically, not about bytes never touching disk. Moderate work: mostly plumbing an existing pipeline to an existing fetcher.
- **(b) Leave them unreadable, but say so clearly.** Cheapest. The resource list would need to distinguish "scanned, and Atlas can't OCR remote files" from a generic empty result, otherwise it looks like a bug.
- **(c) Ask the user to download those specific files manually.** Once a local copy exists, `local_twin_id` resolution (`remote-attachment architecture` §3.3) already picks it up and normal OCR applies. Zero new code, but it's manual work the app is supposed to remove.

**Recommendation:** (a), but only if the user actually cares about those 9 files — worth checking what they are first. If they're a professor's scanned readings for a course that's already over, (b) is fine and honest.

**Status:** Open — needs the user's call. Not blocking anything; logged so it isn't rediscovered later as a mystery.
