# Atlas — Architecture

This document records the technical decisions behind Atlas and the reasoning for each, so future contributors (human or AI) don't have to re-derive them.

## 0. Hard constraint: zero AI integration, zero API fees, anywhere

Atlas itself never calls any LLM or AI API — not Anthropic, not OpenAI, not Google Gemini, nothing. The only reasoning engine is Claude Code, run as a separate process the user drives directly, covered entirely by their existing Claude subscription. This is not a cost-optimization detail to revisit later — it's the same "Atlas owns data, Claude owns reasoning" split from the PRD, made strict: if a feature would require Atlas to make an API call to an AI model, it's out of scope for Atlas, full stop.

This also means every other integration in Atlas must run on a genuinely free tier, with no billing account enabled anywhere:

- **Google Classroom / Drive APIs** — free under normal read-scope usage via the user's own Google Cloud OAuth client (no Google Cloud billing account needs to be attached). (Gmail was considered as a future adapter but descoped from Atlas entirely 2026-07-29 — see `ROADMAP.md`'s "Explicitly out of scope" section.)
- **OCR** — must be a local/offline engine, not a metered cloud API (see §3 below; this ruled out Cloud Vision).

If a future feature seems to need a paid API, the answer is "cut the feature, don't add the cost" unless the user explicitly opts in later.

## 1. Application shell: Electron + TypeScript

Atlas needs to, on one desktop app:

- Render PDFs, images, markdown, and text inline (section 10, Resource Viewer)
- Watch local folders for new files (section 6, Local Storage)
- Talk to Google Classroom and Drive APIs (section 6)
- Support OCR ingestion of handwritten notes (section 7)
- Provide fast full-text search across all of the above (section 14)

Electron was chosen over Tauri and native Python/Qt because:

- It's Chromium-based, so PDF/image/markdown rendering is close to free (`pdf.js`, native `<img>`, any markdown renderer) rather than something to build or bind to.
- Google's official SDKs (`googleapis` npm package) cover Classroom and Drive with no wrapper layer needed.
- File watching (`chokidar`) and packaging (`electron-builder`) are mature and well documented.
- Tauri would produce a lighter binary, but the Rust↔JS bridge adds friction for Google API calls and OCR pipelines with little payoff at V1 scale (single user, single machine).
- Python/PyQt has a better ML/OCR ecosystem, but worse embedded-document-viewer support and a rougher desktop packaging story.

### Menu bar: hidden by default

`BrowserWindow`'s `autoHideMenuBar: true` option is set in `createWindow()` (`main.ts`) — the File/Edit/View/Window/Help bar is hidden by default (saves vertical space) and Alt still reveals it temporarily, standard Electron/Chromium behavior on Windows/Linux for an auto-hidden menu bar. No effect on macOS, which never renders an in-window menu bar to begin with. Per explicit user request.

### Window frame: app-owned (built 2026-08-06)

Atlas uses a frameless `BrowserWindow` so Windows' native title strip does not add a second Atlas title and a separate-looking set of controls above the application. The renderer owns three themed controls — minimize, maximize/restore, and close — in a fixed, background-matched layer at the top edge of the main content area. A narrow `-webkit-app-region: drag` surface moves the window; the controls and all app controls remain `no-drag` so search, dropdowns, and page actions cannot be intercepted. Window controls cross the context-isolated preload bridge through four narrow IPC operations, and maximize/unmaximize events are sent back to the renderer so the restore icon and accessible label stay current. Existing normal bounds/maximized-state persistence remains in the main process. The custom shell is verified through the real Electron window for drag-region CSS, maximize/restore, minimize, and restore behavior.

### Branding and native app icon (built 2026-08-06)

The renderer currently uses cropped, transparent versions of two exact user-supplied reference PNGs in `src/renderer/assets/` while the cap-shaped A mark is being visually approved. `applyTheme()` updates every in-app logo image together, so the sidebar and Settings → About never drift into the wrong contrast. The earlier SVG assets remain beside them as the previous approximation and are not currently active. Native Windows surfaces do not receive the renderer's live theme state, so Electron uses the transparent dark-theme PNG and `electron-builder` uses its matching ICO. `scripts/prepare-logo-assets.js` removes the supplied screenshot backgrounds and refreshes the native PNG; the local `app-builder` tool produces the ICO from it. `app.setAppUserModelId('com.atlas.desktop')` gives Windows a stable identity for taskbar grouping instead of leaving it attached to Electron's development identity.

### Renderer build pipeline: esbuild, added for the notes editor

The renderer (`src/renderer/renderer.ts`) originally had no bundler at all — it's loaded as a plain, non-module `<script>` tag (the window has `contextIsolation: true`, `nodeIntegration: false`, so there's no `require` and no module-level `exports` object either), and `tsc` alone was enough as long as the file avoided `import`/`export` syntax (which makes `tsc` emit CommonJS boilerplate that throws in that environment).

Adding the notes editor (see "Notes" below) needed a real npm UI library — first tried `@toast-ui/editor`, whose published build externalizes its ProseMirror dependencies for bundler consumption and isn't usable from a bare `<script>` tag (later replaced with `@milkdown/crepe`, same constraint applies — a modern editor library assumes a bundler). Rather than hand-vendor a third-party prebuilt bundle of uncertain provenance, `esbuild` was added as a dev dependency solely to bundle `renderer.ts` (`scripts/build-renderer.js`) into one browser-ready IIFE, resolving `import`s of npm packages (and their CSS/font assets) along the way. `main.ts`/`preload.ts` are unaffected — they're proper CommonJS already and still compile via `tsc` directly. Type-checking for the renderer runs as a separate `tsc --noEmit -p tsconfig.renderer.json` step (esbuild transpiles but doesn't type-check). This also means `renderer.ts` can use normal `import`/`export` syntax going forward — the constraint that drove the original workaround no longer applies to that file.

## 2. Data store: SQLite (embedded, local-first)

Atlas maintains "the canonical academic database" (PRD section 15) — course info, metadata, file locations, deadlines, announcements, assignments, OCR text, indexes, and relationships.

SQLite (via `better-sqlite3`) is the store because:

- Single-user, single-machine app → no need for a client-server database.
- Ships as an embedded file — zero setup, trivial backup (copy one file).
- Fully functional offline by default, which resolves one of the PRD's own open questions (Offline Behavior) for the core data layer.
- SQLite's FTS5 extension provides full-text search across notes, OCR text, and metadata (PRD section 14) without introducing a separate search service like Elasticsearch.

Binary blobs (original scans, PDFs, images) are **not** stored in SQLite — they stay on disk in a managed Atlas data directory, with SQLite holding the file paths, metadata, and extracted/searchable text. This keeps the database small and keeps original files trivially recoverable/inspectable outside the app.

The managed data directory is `Downloads/Atlas-Storage/` (course subfolders inside it), not a hidden system app-data path — chosen deliberately so files stay somewhere the user can browse and manually add/remove from without digging through OS-hidden directories. The SQLite database and app config live alongside it under the same folder. This is a **separate folder from the Atlas source repo** (which also happens to live under `Downloads`), specifically so dev/git operations (clone, clean, checkout) can never touch real user data.

Course subfolders under `files/` are named after the course itself (e.g. `files/Data Structures/`), not an opaque ID, so the folder structure stays human-browsable. The name is sanitized for filesystem-invalid characters and computed once at course creation (stored in `courses.folder_name`) rather than derived from the course name on every access — this keeps existing file paths valid even if course-renaming is added later. Uploaded files keep their original filename inside that folder, only disambiguated (`name (2).ext`) on an actual collision.

App-wide UI preferences that shouldn't reset per-course or per-launch (currently just the resource list/icon view mode) live in a small `app_settings` key/value table, read once at startup and written whenever the user changes one — deliberately a single global setting rather than remembered per-course, since the user wants one consistent view across the whole app.

**Course archiving (session 2026-07-28, `open-questions.md` #4).** `courses.archived` existed in the schema from early on but had no UI or product decision behind it until now. Archiving flips only that one flag — every file, note, and deadline for the course is left completely untouched, unlike Delete (a separate, destructive action that removes all of it). Archiving/unarchiving is available from a course card's right-click menu and from a button on the course's own detail page (`courses:setArchived` IPC handler). The Courses page shows either active courses or archived ones via a single toggle — never both mixed in one list, so a card on screen is unambiguous about which state it's in (`dashboard:courseSummaries` takes an `archived` boolean and returns one set or the other, defaulting to active for every existing caller that doesn't pass one). An archived course is excluded from the Classroom sync loop (`syncClassroomCourseworkForMappedCourses` in `googleClassroom.ts`) so it stops pulling in new content, but stays linked — unarchiving picks sync back up immediately with no reconnect needed. It's also excluded from the Classroom/Ashoka course-mapping name-match suggestion, same as it always was (`suggestExistingCourse` already filtered `archived = 0`). Global search deliberately was **not** changed — `rebuildSearchIndex()` never filtered by archived status, so archived-course notes/resources stay fully searchable; the point of archiving is decluttering the course list, not hiding material.

The Storage settings page includes a guarded local reset for this managed data. After two confirmations (including typing `DELETE`), Atlas removes the local academic workspace: database content rows, managed files, course/general agent memory, exports, readiness fixtures, search index data, watched-folder mappings, pending remote imports, and local backups. It preserves the Google OAuth refresh tokens and `config/google-oauth-client.json`, preserves general app preferences, and never deletes anything in Google Drive or Classroom. Source-folder selections and sync status are cleared so a later sync can repopulate a deliberately empty local workspace; the reset does not revoke or disconnect the Google accounts.

## 3. OCR: local, offline (Tesseract.js)

Handwritten notes are first-class (PRD section 7). The originally considered option — Google Cloud Vision — is a metered, paid API and is ruled out by the zero-API-fees constraint (§0). Instead, OCR runs locally via Tesseract.js: free, offline, no request costs, no credentials.

The honest tradeoff: Tesseract handles printed text well but handwriting recognition quality is meaningfully worse than a paid cloud OCR model. That's an accepted cost of the no-fees constraint, not an oversight. A possible future improvement, still zero-cost, is Windows' built-in ink/handwriting recognition (`Windows.UI.Input.Inking`), which runs on-device and ships with the OS — worth prototyping in Phase 2 if Tesseract's handwriting accuracy proves too poor to be useful, but not a Phase 2 blocker.

Both the original scanned image and the extracted OCR text are retained regardless of engine (per PRD section 7) — OCR failure or low confidence never discards the source image.

### Implementation (Phase 2, built)

**Primary input is multi-page PDF scans** (Adobe Scan and similar apps), not individual photos — confirmed directly with the user before building this, since it changes what "OCR pipeline" actually has to do. **One imported file = one note**, however many pages a PDF has: `notes.image_path` (already in the schema ahead of this feature) holds the original scan file itself — image or PDF, unmodified.

**OCR is opt-in per note, not automatic on import** (changed shortly after shipping the first version, which did run it automatically). The user tested it against their actual handwriting and found local Tesseract's accuracy too poor to trust silently — and separately pointed out that Claude Code can already read a handwritten scan directly via vision, today, with no Atlas feature required, which is a better fit for handwriting than OCR ever will be. Decision (see `open-questions.md` #18): importing a scan just creates a blank note with the original file attached (`is_handwritten = 1`, `image_path` set, `content_markdown = ''`, titled from the filename since there's no text yet to derive a title from) — no OCR runs. A separate "Run OCR" button in the note editor (visible only for handwritten notes, next to "View original scan") runs `extractTextFromScan` on demand and shows the raw result in a review panel (`#note-ocr-preview`) with **Discard**/**Insert into note** — nothing is written to the note until the user explicitly accepts, at which point it goes through the exact same `notes:updateContent` path a normal edit would (title re-derives from it automatically, same as typing). `notes.ocr_text` still exists in the schema but is no longer populated by this flow — OCR output is either accepted straight into `content_markdown` or thrown away, there's no separate "last OCR run" record kept.

- **`src/main/ocr.ts`**: `extractTextFromScan(filePath, onProgress)`, unchanged from the original implementation — only *when* it's called changed. Images go straight to a Tesseract `recognize()` call. PDFs go through `pdfjs-dist` (page count + per-page rendering) → `@napi-rs/canvas` (rasterizes each page to a PNG buffer, no native build toolchain required, unlike `canvas`/node-gyp) → Tesseract `recognize()` on each page buffer, joined with `\n\n---\n\n`. The shared Tesseract worker (module-level singleton, avoids repeated cold-start cost) is no longer explicitly terminated after an import batch, since there's no batch anymore — it just stays warm across on-demand `notes:runOcr` calls for the rest of the session, cleaned up on `window-all-closed`.
- **Genuinely local/offline, not just "no cloud OCR API call."** Tesseract.js doesn't ship its English language data in the npm package (fetches `eng.traineddata` from a CDN by default) and pdfjs needs its standard-14 font metrics for reliable text-PDF rendering (also CDN-fetched by default) — both are vendored in this repo (`assets/tessdata/`, `assets/standard_fonts/`) and copied into `dist/main/` by `scripts/copy-assets.js`, with `langPath`/`standardFontDataUrl` pointed at the local copies. Without this, "local, offline" OCR would silently phone home on first use.
- **`pdfjs-dist` v6 ships ESM-only** (no CommonJS build), which this project's main process compiles to (same constraint already documented for `marked` in `preview.ts`, solved there by pinning an older major version — not an option here, since there's no CJS-compatible pdfjs-dist release with this rendering API). Instead, the dynamic `import()` is routed through `new Function('specifier', 'return import(specifier)')` — confirmed by inspecting `tsc`'s actual output that a plain `await import(...)` gets rewritten to `require(...)` under `module: commonjs` (which throws `ERR_REQUIRE_ESM` on an ESM-only package), while hiding the import behind `new Function` keeps it as a genuine dynamic import at runtime, invisible to TypeScript's static transform.
- **Import UI**: "+ Import scan" on the Notes page opens the existing course-picker modal (`#course-picker-overlay`) in a new `'scan'` mode — same search/select-course UX Upload/New Note already use. Supports multi-select (native dialog: `properties: ['openFile', 'multiSelections']`) and multi-file drag-and-drop, each file becoming its own (blank, un-OCR'd) note. Import itself is now just a file copy, so it's fast — no progress channel needed for it anymore.
- **Viewing**: a "View original scan" toggle in the note overlay (visible only when `is_handwritten`) swaps the editor out for a panel rendering `image_path` — not a split layout with both visible at once; toggling hides `#note-editor-root` and shows `#note-scan-panel` in the same space, and vice versa (the user's explicit preference — flipping between the scan and the note's own content, not shrinking both into half the space). Reuses the exact same `Preview` type and rendering branches (`getPreview()` in `preview.ts`) the Resources page's preview modal already uses, via a new `notes:getScanPreview` IPC handler, so a handwritten note's scan is just "a file on disk," no different from a resource's. "Run OCR"'s review panel and the scan view are kept mutually exclusive too (opening one closes the other) rather than letting both stack. **The scan is what shows by default when opening a handwritten note**, not the editor — a handwritten note's `content_markdown` starts blank until OCR is run and explicitly accepted, so defaulting to the editor would look broken (an empty page) on first open; the toggle button's icon/label flips to indicate which view it would switch *to* (`updateScanToggleLabel` in `renderer.ts`).
- **On-demand OCR for Resources PDFs** (open-questions.md #18, built after the user asked directly): the same `extractTextFromScan` pipeline, now also reachable from the Resources preview modal (`#preview-overlay`) for any `kind = 'pdf'` resource, via a "Run OCR" button next to fullscreen/close. This targets a different case than handwritten notes — a typed/printed PDF with no text layer (e.g. a scanned book) — but keeps the exact same never-silently-trusted shape: `resources:runOcr` returns extracted text without touching the DB, the renderer shows it in a review panel (`#preview-ocr-review`), and only an explicit "Save extracted text" (`resources:saveOcrText`) writes it to a new `resources.ocr_text` column and calls `rebuildSearchIndex()` to make it searchable. Discarding leaves the resource exactly as it was — same as `notes.ocr_text`, but for a resource rather than a note, since a resource has no editable `content_markdown` to insert into. The original PDF is always what's shown by default on open (unaffected by this feature — Run OCR is a strictly opt-in extra action, never a replacement default view).
- **Recurring `[hidden]`-vs-own-selector bug, 4th instance**: `.split-preview-actions button` set `display: flex` unconditionally — harmless while every button in that shared header was always visible, until "Run OCR"/"View original scan" became the first ones conditionally hidden per-note. Caught by a `verify-app.js` assertion added specifically to check a typed note's `#note-view-scan` is genuinely hidden (not assumed from the `hidden` attribute alone), fixed by scoping the rule to `:not([hidden])`, same pattern as the three prior instances.
- **Two-stage Escape, superseding the session-24 "Escape never closes a note" decision.** That decision was made when Escape closing the note risked discarding an in-progress selection mid-typing — still a real concern, so Escape still doesn't close a note outright while actively editing. Instead: the first Escape while focus is in the title input or the Milkdown surface just blurs out of editing (note stays open); a second Escape, with nothing focused, then closes it — and if the note was only being viewed to begin with (nothing ever focused), a single Escape closes it immediately, same as the Resources preview. The title input's own Escape handler (revert rename + blur) calls `stopPropagation()` so it doesn't also trigger the global handler's close-check on the same keypress — without that, the field would already show blurred by the time the event bubbles up, making a single Escape both revert *and* close in one press instead of two.

## 4. Sync layer

Each data source (Classroom, Drive, local folders, manual upload) is implemented as an independent sync adapter that writes into the same canonical schema. Adapters are responsible only for pulling source data and normalizing it — course/course-resource association, deduplication, and relationship-building happen in a shared layer downstream of all adapters, so no single source's quirks leak into the core data model.

### Sync scheduling (built 2026-07-28, `open-questions.md` #2)

Drive and Classroom used to run on unconditional, hardcoded schedules baked directly into `app.whenReady()` (Drive: `setInterval(..., 20_000)`; Classroom: launch only) — invisible to the user and impossible to change without editing code. This is also how the Classroom adapter's real sync bug (§4b) went unnoticed for weeks: nothing in the UI could ever have shown that syncing was silently failing every single time.

- **One `app_settings` string per source** (`sync_config_drive`/`sync_config_classroom`): `'off'`, `'launch'`, or `'interval:<seconds>'` — chosen as one combined value rather than a separate mode/interval pair specifically so a Settings `<select>`'s own `value` is exactly what gets persisted, no translation layer in between. Unset falls back to defaults that reproduce the prior hardcoded behavior exactly (Drive `interval:20`, Classroom `launch`), so this is a pure generalization for an existing install, not a behavior change, unless the user touches the new controls.
- **`applySyncSchedule(source)`** (`main.ts`) is the single place scheduling actually happens: clears any existing timer for that source, then — unless the mode is `'off'` — runs one sync immediately and, for `'interval'` mode, starts a fresh recurring timer at the configured period. Called once per source at launch, and again immediately from the `sync:setConfig` IPC handler whenever the user changes the dropdown, so a change is live without a relaunch.
- **`'off'` only disables the background schedule, never a user's own explicit action** — Connect, setting the Drive folder, and "Sync now" all still run regardless of the configured mode, since those are deliberate one-off actions, not the recurring background sync this setting governs.
- **Status, not just a schedule**: `sync_<source>_last_success`/`sync_<source>_last_error` (`app_settings`) are updated on every sync attempt, automatic or manual, and rendered in Settings as a relative-time line ("Last synced: 2m ago") with any error shown inline. A Classroom sync with some per-course failures still advances `last_success` (real work did happen) while keeping the error text visible alongside it, rather than collapsing "mostly worked" into either a clean success or a clean failure. Every result also emits a `sync:statusChanged` event to the renderer after the database write, so an open Settings page reflects background results without navigation or relaunch.
- **Reconnect performs a confirmed first scan**: the Drive/Classroom connect handlers clear the stale authorization error, then await `applySyncSchedule(source, true)`. The force flag runs one scan even when the saved background mode is Off; otherwise it follows the configured launch/interval schedule. The reconnect button therefore returns only after Atlas has a current success or failure state to display.
- **UI**: a new "Sync" section at the top of Settings > Sources, reusing the `.settings-row`/`.settings-row-label`/`.settings-row-hint` classes already established by the General tab's Theme/Accent rows rather than introducing new ones. Classroom's previous standalone "Sync now" button (with its own `alert()`-based error popup) was removed in favor of this single, consistent per-source control — two visually different "sync now" affordances for the same source would have been the kind of inconsistency worth avoiding on the first pass, not fixing after the fact.
- **Expired/revoked OAuth recovery (built 2026-08-06):** sync catches normalize Google's `invalid_grant` / expired-or-revoked-token failures into the shared `last_error` state and expose an `authRequired` flag through `sync:getStatus`. That source's interval is stopped so Atlas does not repeatedly emit the same failure. Settings then shows a source-specific reconnect action and explains that authorization must be renewed; the existing refresh token is not deleted automatically, so the user can reconnect directly. A successful reconnect clears the stale error and reapplies the configured schedule, while Drive and Classroom remain independent. Other sync failures keep their existing error text and retry behavior.

**Local folder watching**, the first non-manual adapter, uses `chokidar` and an explicit, user-configured `watched_folders` table (`course_id` ↔ `folder_path`, one course per folder) — not auto-detection of which course a file "probably" belongs to. This was a deliberate call, not a default: guessing course association from file content/location would be Atlas inferring meaning from academic content, which is Claude's job per the "Atlas owns data, Claude owns reasoning" rule (`CLAUDE.md`), not something to quietly build into a sync adapter. A watcher is started per row at app launch and whenever a folder is newly added; new files are copied into the course's managed storage (identical path/naming logic to manual upload) and inserted as `resources` with `source = 'local_folder'`. Each imported resource also stores its original watched-folder path (`resources.watch_source_path`) purely so a watcher restart — which re-scans a folder's existing contents by design — can recognize "already imported" and skip re-importing, not to track live source-file state.

Deletion is mirrored too: if a source file disappears from a watched folder, the resource it produced is deleted along with its managed-storage copy — via `chokidar`'s `unlink` event while the app is running, and via a reconciliation pass (compare each `local_folder` resource's `watch_source_path` against the filesystem) whenever a folder's watcher starts, to catch deletions that happened while Atlas wasn't open. This keeps watched-folder resources honest with their source rather than leaving stale entries that error when opened.

**Every course's own managed storage folder is watched too** (`startWatchingCourseStorage()` in `main.ts`), separately from the opt-in watched folders above and with no course-mapping decision involved — a course's own `files/<course>/` folder is unambiguously that course's. This exists because §2 explicitly designs the data directory to be user-browsable and hand-editable ("files stay somewhere the user can browse and manually add/remove from"); without a watcher on it, that promise wasn't actually true — a file deleted by hand from `Downloads/Atlas-Storage/files/<course>/` left a `resources` row behind that errored with "resource not found" when opened, and a file dropped in by hand was invisible to Atlas until the next manual refresh. Same `add`/`unlink` + startup-reconciliation pattern as watched folders; the only difference is `add` events check `file_path` (not `watch_source_path`) to detect "this is our own copy that just landed" and skip re-importing it, since these files are already inside managed storage rather than being copied in from elsewhere.

**Real bug fixed 2026-07-28 (`open-questions.md` #26):** `reconcileCourseStorage()` (the "did this file disappear from disk" check the watcher above runs on every launch) checked every resource in a course, including `kind = 'link'` Classroom attachments — whose `file_path` is an external URL, not anything on this machine's disk. `fs.existsSync()` on a URL always returns `false`, so this function deleted every Classroom-linked resource on every single launch; the Classroom sync that runs right after then recreated them all with a fresh `added_at`, which is why the Dashboard's "Recently added"/"What changed today" widgets falsely showed every synced Classroom file as brand-new on every launch. Fixed by excluding `kind = 'link'` resources from this check entirely — they were never something it was meant to cover. Caught in the same pass: `resources` never had the partial unique index on `classroom_attachment_id`/`drive_file_id` that the equivalent Classroom/Drive upsert tables (`assignments`, `deadlines`, `announcements`) already had (`database.ts`'s `migrate()`), so nothing was actually stopping a duplicate row if the delete-then-recreate cycle above hadn't been silently masking it — added, with a one-time de-dup pass first since `CREATE UNIQUE INDEX` fails outright if duplicates already exist. The already-corrupted `added_at` values on existing rows were repaired by a one-time startup pass (`repairClassroomResourceAddedAtOnce()` in `main.ts`, gated by an `app_settings` flag so it only ever runs once) that looks up each resource's real Classroom posting time via the announcement/assignment/classwork item it came from — `assignments` gained a new `posted_at` column for this, mirroring `announcements.posted_at`/`classwork_materials.posted_at`, which already existed but weren't being used to set a resource's `added_at` at all (everything defaulted to "whenever the sync happened to run").

### 4a. Google Drive adapter (Phase 3, built first — see `open-questions.md` #19)

Built ahead of Classroom/Gmail (a user decision, reordering the phase) because it directly replaces a real, immediate pain point: manually relaying phone scans through a Discord self-chat, then downloading and re-uploading on the laptop. The user was explicit the inbox must be a real Google Drive folder that Atlas scans via the Drive API — not a local folder kept in sync by a desktop client, which would have just been an extension of the existing local `watched_folders` mechanism above. A local-folder prototype was started, then reverted once that requirement was clear.

- **OAuth: bring-your-own client, loopback-redirect flow.** Per `open-questions.md` #7, Atlas ships no credential of its own — the user creates their own free Google Cloud project (personal account, not the college Workspace one used for the Classroom adapter — no reason to route a personal scans folder through college infrastructure), enables the Drive API, and downloads a **Desktop app** OAuth client credential (`google-oauth-client.json`), copied into `Atlas-Storage/config/` (`getConfigDir()`/`getGoogleCredentialsPath()` in `paths.ts`) — never the git repo, since it's tied to the user's own Cloud project. `src/main/googleAuth.ts` implements the loopback-redirect flow (RFC 8252, the only flow Google still supports for installed apps now that the old out-of-band flow is retired): a local HTTP server on an ephemeral port catches the single redirect after the user approves access in their real browser (`shell.openExternal`), exchanges the code for tokens, and stores just the refresh token in `app_settings` (`google_drive_refresh_token`) — `google.auth.OAuth2` handles refreshing the short-lived access token automatically from there on every API call.
- **Testing-mode caveat, accepted deliberately.** The OAuth consent screen stays in Google's "Testing" publishing status rather than going through verification (which would need a live privacy policy and, for a scope like Drive, a security assessment — real overkill for a personal single-user tool). The accepted cost: refresh tokens for sensitive/restricted scopes expire after about 7 days, so the user just reconnects (one click through the consent screen again) periodically — not a re-setup, just a re-approval.
- **Scope: `drive.readonly`.** Atlas only ever downloads a copy into local managed storage; it never writes back to Drive.
- **One designated "inbox" folder**, not the whole Drive — the user pastes the folder's URL (or raw ID) from their browser's address bar (`setDriveFolder()` in `googleDrive.ts`, no Google Picker widget involved), validated by fetching it and confirming it's actually a folder before saving. **Recursively scans subfolders too** (depth-capped at 20 purely as a sanity guard, not a real expected limit) — the user organizes the inbox folder with subfolders (e.g. one per course) and still wants every file anywhere underneath it to count, not just ones sitting directly in the top-level folder.
- **Polling, not push.** True push (Drive's `changes.watch` webhook) needs a public HTTPS endpoint, which doesn't fit a local desktop app — the user explicitly accepted ~15–30s polling while Atlas is open (implemented as a 20s `setInterval`) plus a full scan on every launch as the realistic "near real-time" tradeoff.
- **Review, not auto-import.** A new Drive file is inserted into `drive_pending_files` (drive_file_id, name, mime_type, modified_time), not turned into a resource/note automatically — which course and which type (Resource / Note) it becomes is a user decision, same reasoning as watched-folder course mapping (`open-questions.md` #11) and "Atlas owns the data" (`CLAUDE.md`). The Dashboard's Google Drive widget shows a pending count and a "Review new files" button that opens a panel (`#drive-review-overlay`) listing each pending file with a per-row course-select + Resource/Note type-select, importable individually or in bulk (checkbox + a shared bulk course/type selection applied to every checked row). Closing the panel ("Later") doesn't lose anything — the pending list is exactly what a fresh scan would find again.
- **Import dispatches to the exact same buffer-based paths manual upload/drag-and-drop already use** (`importBufferIntoCourse` for Resource, `importScanBufferIntoNote` for a Note that's a scan/image file, or a new `importTypedNoteFromBuffer` for a Note that's plain text/markdown) — a downloaded Drive file is just a buffer, no different from a dropped one. Each gets `drive_file_id` recorded on the resulting `resources`/`notes` row (new nullable column on both tables) so a future scan's dedup check (`alreadyImported()`) recognizes it and never re-surfaces it as new.
- **Ignore, not just import.** A pending file can be explicitly ignored (`ignoreDrivePendingFile()`) — the row stays in `drive_pending_files` with `ignored = 1` (rather than being deleted), so the table's `UNIQUE` constraint on `drive_file_id` keeps a future scan's `INSERT OR IGNORE` from re-adding it as "new," while `listPendingDriveFiles()` filters `ignored = 0` so it no longer shows up in the count/review panel. Nothing is downloaded — the opposite of import, not a soft version of it.
- **Deletion is reconciled on every scan**, not just at watcher start (there's no persistent watcher process here, just polling) — a pending file's `drive_file_id` no longer present in a fresh recursive listing gets removed from `drive_pending_files`, so a file deleted from Drive before ever being reviewed doesn't linger forever as a dead, unimportable entry. A file already imported is untouched by this — once downloaded, it's a fully local, independent copy; Drive is never consulted again for it.
- **Re-uploading "the same" file is not deduplicated across distinct uploads** — Drive assigns a new file ID to a genuinely new upload (even same name/content), which Atlas has no way to relate to a prior import, so it's treated as a new pending file. Using Drive's own "Replace" on an existing file *does* keep the same ID, which means an edited/replaced file that was already imported will keep being silently skipped (already-imported check matches by ID) rather than re-triggering review — this is a one-time-import model, not a live two-way sync, and edits made on Drive after import don't flow back into Atlas.
- **Native Google Docs/Sheets/Slides are skipped at scan time** (mimeType prefix `application/vnd.google-apps.`) — they can't be fetched via Drive's `alt: 'media'` download, which only works for regular binary/text files. Not a real gap for this workflow, since Adobe Scan/tablet note apps produce real files (PDF/image/text/markdown), never native Google Docs.
- **Known gap, not built**: a `google-auth-library` version-duplication issue in TypeScript (googleapis' own dependency tree hoists a second, separately-typed copy of that package) meant the `OAuth2Client` type couldn't be imported directly without a type-incompatibility error — worked around by deriving the type from `google.auth.OAuth2` itself (`InstanceType<typeof google.auth.OAuth2>` in `googleAuth.ts`) rather than importing it from the package.
- **Not covered by `scripts/verify-app.js`** — this needs a live Google account/OAuth token, which the automated suite has no way to provide. Verified manually against the user's real personal Google account and a real Drive folder instead (OAuth consent round-trip, folder link validation, top-level + subfolder file detection, import into both Resource and Note paths, ignore, and stale-pending cleanup after deleting an unreviewed file from Drive).

### 4b. Google Classroom adapter (Phase 3, built right after Drive — see `open-questions.md` #20)

Unlike Drive (flat files, no course concept), Classroom has real course objects that must map onto Atlas's own `courses` table — a mapping mechanism that didn't exist before this adapter.

- **OAuth: same bring-your-own client as Drive, separate connection.** `src/main/googleAuth.ts` gained a second, parallel set of scope/token plumbing (`CLASSROOM_SCOPES`, `google_classroom_refresh_token`) rather than a fork of the whole module — the loopback-redirect flow, `loadClientCredentials()`, and the `OAuth2Client` type workaround are already scope/account-agnostic. Classroom is expected to be connected against the user's **college Workspace account**, not the personal account used for Drive (`open-questions.md` #8), so it has its own connect/disconnect state and refresh token, independent of Drive's.
- **Scopes: `classroom.courses.readonly`, `classroom.coursework.me.readonly`, `classroom.announcements.readonly`, `classroom.courseworkmaterials.readonly`** — `.me` rather than `.students` for coursework, since `.students` requires teacher/domain-admin-level access and this is a student account. `courseworkmaterials.readonly` (added 2026-07-27 alongside Classwork sync, `open-questions.md` #21) has no `.me` equivalent — it's the same scope regardless of teacher/student context — and was initially missed, causing a real `"Request had insufficient authentication scopes"` failure on a live Connect attempt; a previously-issued refresh token doesn't retroactively pick up a newly-added scope, so the user has to disconnect and reconnect Classroom once after this change.
- **Standing gotcha for any future scope change (not specific to this adapter — applies to Drive's `SCOPES` too):** a refresh token is frozen at whatever scopes were granted the moment the user approved the consent screen. Editing `CLASSROOM_SCOPES`/`SCOPES` in code changes what Atlas *requests* on the next fresh OAuth grant, but does nothing to a token issued under the old list — Google has no mechanism to retroactively add a scope to an existing token. **Whenever a scope is added to either list, the user must disconnect and reconnect that specific Google connection (Dashboard-level Connect/Disconnect, not any per-course link/unlink action) once**, or every API call needing the new scope will fail with `"insufficient authentication scopes"` no matter how correct the rest of the code is. This surfaced for real on 2026-07-27 when `courseworkmaterials.readonly` was added — worth calling out explicitly in any future PR/session that touches either scopes list.
- **Course mapping is the one place review is gated — explicit, never auto-assigned.** A Classroom course seen via `courses.list` that isn't yet linked to an Atlas course lands in `classroom_pending_courses` (mirrors `drive_pending_files`'s shape: detected, reviewed, then resolved), with a `suggested_course_id` computed by a case-insensitive name match against existing Atlas courses — a suggestion pre-filled in the review panel's picker, never applied on its own. The Dashboard's Classroom widget shows a pending count and a "Review new courses" button opening `#classroom-review-overlay`, structurally identical to the Drive review panel (same CSS Grid alignment between the bulk-header row and per-row rows). Resolving a row either links an existing Atlas course (`linkClassroomCourseToExisting` — sets `courses.classroom_course_id`, leaves everything else about the course untouched) or creates a new one (`classroom:mapCourseToNew` in `main.ts`, reusing the exact folder-naming/creation steps `courses:create` uses, then linking it) — same "explicit mapping only" reasoning as watched-folder course mapping (`open-questions.md` #11). Either resolution path immediately triggers a `scanClassroomAndNotify()` afterward (same reasoning as `setDriveFolder`'s immediate re-scan) — confirming a mapping used to leave the course looking empty until the next launch/"Sync now" click, since linking alone doesn't pull coursework; fixed the same session it was first noticed.
- **Real-world use surfaced the actual intended course-mapping workflow.** After building this, the user tried mapping some already-past Classroom courses and pointed out their real intent was the reverse order: pre-create *next* semester's Atlas courses first (via the Ashoka Planner import, §4c), then let Classroom's review panel **link** to those already-existing courses rather than create new ones from Classroom data. "Map to existing" already supports this directly — the gap was just that nothing existed yet to pre-create the courses from, which §4c now fills.
- **Once a course is mapped, its coursework/announcements/classwork auto-import — no per-item review.** This is a deliberate departure from Drive's per-file gate: the ambiguity a review step exists to resolve (which course does this belong to? what type is it?) doesn't apply to Classroom coursework, since the API already returns typed, course-scoped data — a `courseWork` item is unambiguously an assignment in a specific already-confirmed course. `syncClassroomCourseworkForMappedCourses()` upserts by the Classroom item's own external ID (`assignments.classroom_coursework_id`, `announcements.classroom_announcement_id`, `classwork_materials.classroom_coursework_material_id` — each backed by a partial `UNIQUE` index added in `database.ts`'s `migrate()`, since SQLite's `ALTER TABLE ADD COLUMN` can't add a `UNIQUE` constraint directly to an existing table), so a re-sync updates the same row rather than duplicating it.
- **The actual "nothing synced" bug was an invalid partial-index `ON CONFLICT` clause, not the missing per-course guard (found 2026-07-27, same day, after a real Connect test still failed post-fix — `open-questions.md` #21).** `upsertAssignment`/`upsertDeadline`/`upsertAnnouncement` targeted a *partial* unique index (`WHERE classroom_x_id IS NOT NULL`) but put that predicate after `DO UPDATE SET` — SQLite requires it restated immediately after the conflict column list (`ON CONFLICT(col) WHERE col IS NOT NULL DO UPDATE SET ...`) to accept a partial index as a valid conflict target at all. Getting this wrong meant `db.prepare()` itself threw `"ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint"` unconditionally, every time, before the sync loop even started — confirmed by preparing both versions directly against the real `atlas.db`. This was very likely broken since the adapter was first built, not something the try/catch work introduced. Fixed by moving the `WHERE` clause to right after the column list on all three.
- **Each mapped course is still synced inside its own `try`/`catch`** (a real, worthwhile fix kept from the first pass, just not what was actually causing the empty syncs): one course's API call throwing no longer aborts every other mapped course's sync. Failures are collected as `{courseId, courseName, message}[]` and returned all the way up through `scanClassroomAndNotify` → `classroom:syncNow`/the mapping handlers/the new per-course connect handler → the renderer, which surfaces them via `alert()` instead of only `console.error`.
- **Assignments mirror into the existing `deadlines` table too**, keyed by the same `classroom_coursework_id` (a new nullable column there as well) — `deadlines` already has real Dashboard/UI support, so a synced assignment is immediately visible without building a new Assignments screen in this pass. Announcements/Assignments/Classwork now have a real UI surface (course-detail sections, see below) — the earlier "no UI surface at all" gap for announcements is closed.
- **Classwork (the ungraded `courseWorkMaterials` tab, distinct from graded `courseWork`) gets its own `classwork_materials` table** (course_id, title, description, posted_at, `classroom_coursework_material_id` unique) — added 2026-07-27, was previously never fetched at all.
- **Attachments are Drive-link resources (`resources.kind = 'link'`), not downloads** — redesigned 2026-07-27 per the user's explicit preference ("drive might be better for me as that means less files on my laptop"). `file_path` holds the external URL directly (Drive `alternateLink`, or a link/YouTube/Form material's own URL); nothing is downloaded, so this no longer depends on Drive also being connected. This also closes the earlier "link/YouTube/Forms materials have nothing downloadable" gap — a link-kind resource represents any material type uniformly. Opening one calls `shell.openExternal` (`preview.ts`'s new `'link'` `Preview` type, and a `kind === 'link'` branch in the resource context menu) instead of routing through the local preview server, which only ever served real local files.
- **Per-course "Connect to Classroom" button** (course detail page, next to Files/Watched-folders) — added 2026-07-27. `classroom:listAvailableCoursesForLinking()` lists live Classroom courses not yet mapped to any Atlas course; a small picker overlay links the course the user is already looking at directly, via the existing `linkClassroomCourseToExisting`. This is the workflow the user actually described wanting (raised 2026-07-26): pre-create next semester's courses via the Ashoka Planner import (§4c), then connect each one to Classroom directly, rather than only being able to map via the discover-new-courses review panel.
- **Per-course "Disconnect" is destructive by design (user's explicit choice, `open-questions.md` #21)** — it doesn't just clear `classroom_course_id`, it deletes everything synced from that link for that course (`deadlines`/`assignments`/`announcements` with `source='classroom'`, that course's `classwork_materials` rows, and any remaining `source='classroom'` `resources`), all inside one `db.transaction()`. This is the real "undo" for connecting the wrong Classroom class — the original version only unlinked, leaving wrongly-imported content stuck with no way to remove it, which the user hit in practice. The renderer confirms first (`showConfirm`) since it's irreversible. The Dashboard's global "Disconnect Google Classroom" (revoking the OAuth connection entirely) is unchanged — still token-only, since it isn't scoped to one course's mapping.
- **Course-detail Announcements/Assignments/Classwork sections** — three new inline sections (same visual idiom as the existing Deadlines/Watched-folders sections; course detail had no tab pattern at the time this was built — it gained one later the same session, see §12), shown only once `courses.classroom_course_id` is set. Backed by a single `classroom:getCourseContent(courseId)` handler that also joins each assignment/classwork item to its link-kind resources.
- **No background polling, unlike Drive.** `scanClassroomAndNotify()` runs once at `app.whenReady()` and from an explicit "Sync now" button (`classroom:syncNow`) — no `setInterval`. Classroom content changes far less often than a Drive inbox, and this avoids unnecessary API load against the college account. See `open-questions.md` #2 for the reasoning.
- **Not covered by `scripts/verify-app.js`** — same reason as Drive: needs a live OAuth token and real Classroom course/coursework data, which the automated suite has no way to supply. Verified manually against the user's real college Workspace account instead.
- **Conflict handling for locally-edited/deleted-at-source coursework (built 2026-07-28, `open-questions.md` #3).** Until this, `upsertDeadline`/`upsertAssignment` unconditionally overwrote `title`/`due_at`/`description` on every sync — editing a Classroom-synced deadline (e.g. correcting a due date the professor announced verbally) was silently reverted on the next launch, and nothing ever reconciled coursework deleted at the source, unlike Drive's `drive_pending_files`. Fixed with:
  - **Per-field protection, not whole-row locking**: `deadlines.local_overrides` (comma-delimited field names the user has edited since the last sync) is checked via a `CASE WHEN instr(...) THEN <existing> ELSE excluded.<value> END` in `upsertDeadline`'s `ON CONFLICT DO UPDATE`, so an overridden field survives a re-sync while a field the user never touched still picks up genuine Classroom updates — the user chose this over the simpler "stop syncing this row once edited" specifically because a moved deadline is the update least worth missing.
  - **`deadlines.classroom_title`/`classroom_due_at`** shadow Classroom's current values on every sync regardless of overrides — this is what makes `deadlines:resetClassroomOverrides` (a new IPC handler, wired to a "Reset to Classroom version" button in the deadline viewer) a purely local operation with no fresh API call needed.
  - **Reconciliation**: `syncClassroomCourseworkForMappedCourses` now computes the live courseWork ID set per course on every sync and flags any `deadlines`/`assignments` row whose coursework has disappeared as `classroom_removed = 1` (cleared if it reappears) — surfaced in the UI as a greyed row + badge, never auto-deleted, since the row may carry a description/`@`-mentions the user attached. The user's existing Delete action is the dismiss mechanism.
  - `assignments` gained the same `classroom_removed` flag for display consistency in the Assignments tab, but no per-field override tracking — assignments has no direct editing UI; the user always edits the mirrored `deadlines` row instead (confirmed via `openAssignmentDetail` in `renderer.ts`, which routes an assignment click to its linked deadline).
  - `dashboard:stats`/`dashboard:upcomingDeadlines` also exclude `classroom_removed = 1`, alongside the existing `stale_import = 0` — the full Calendar page intentionally keeps neither filter.

### 4c. Ashoka Planner course import (local, one-shot, user-invoked — `open-questions.md` #15)

Not a sync adapter in the OAuth/API sense — this is a **local-file-to-local-file read**, no network involved. The user built a separate app, `ashoka-planner`, that tracks course registration for a semester in its own SQLite database (`data/planner.db`, real path picked once via a native file dialog and remembered in `app_settings` under `ashoka_planner_db_path`). Its schema (verified directly against `scripts/pipeline/schema.sql` and `scripts/registration_server.py`, not guessed) has a `slot` table where a row's `status` becomes `'secured'` once that course is actually locked in for the semester, with the course's own fields (code, title, category, faculty, credits) embedded as `current_course_snapshot_json`; a `course_description` table keyed by section code carries a real description (`overview`); and a singleton `student_profile` row carries `current_semester`.

- **Genuinely one-shot and user-invoked, not automatic — the user was explicit about this.** No background scan, no polling, no pending-review table that persists between sessions like Drive/Classroom. A "Import from Ashoka Planner" button on the Courses page toolbar (`src/main/ashokaPlanner.ts` for the read side, `ashoka:*` IPC handlers in `main.ts` for the Atlas-side course creation) opens a plain checkbox review list of currently-secured courses and does nothing until the user presses "Import selected."
- **Term is user-confirmed, not auto-derived — a real data gap found by checking against the actual file.** An initial version tried normalizing `student_profile.current_semester` into Atlas's `"Season YY"` term format, assuming it looked like `"Spring 2026"`. Checked directly against the user's real `planner.db` and found `current_semester` is just a bare season name (`"Monsoon"`) with no year, and `current_year` is an ordinal program-year (e.g. `3`), not a calendar year — there's no reliable way to derive `"Monsoon 26"` from what's actually there. Fixed by asking instead of guessing: the review panel has a term text input, pre-filled with the raw season name as a hint, that the user confirms/edits before importing; `getAshokaSemesterHint()` returns that raw hint only, never a fabricated year.
- **Dedup on re-run, not duplication** — computed at import time (`ashoka:importCourses`) against the term the user just confirmed, since list time has no reliable term to check against yet. A candidate matching an existing Atlas course by `code` + that confirmed `term` is skipped rather than duplicated; the result reports how many were skipped so re-running the import after a registration change is safe and visibly so.
- **New `courses.description` column** — the one schema gap `open-questions.md` #15 identified up front (`courses` previously had `name`/`code`/`term`/`folder_name`/`archived`/`source`/`classroom_course_id` only), added via the same `ALTER TABLE ... ADD COLUMN` migration pattern used throughout `database.ts`. Populated from `course_description.overview`; `null` for manually-created or Classroom-mapped courses, which have no description source.
- **This is the other half of the Classroom course-mapping workflow (§4b).** A course imported here can later be linked (not re-created) when Classroom's course-mapping review panel finds the matching Classroom course — "map to existing" rather than "create new."
- **Not covered by `scripts/verify-app.js`** — needs a real `planner.db` with real secured-course data, which the automated suite has no way to supply. Verified manually against the user's own ashoka-planner database instead.

`deadlines` already mirrors Classroom assignments (§4b), so "combines deadlines and assignments" was already true structurally by the time this was built — neither the widget nor the Calendar page needed a separate merge step, both just query `deadlines`.

- **Dashboard widget** (`#dashboard-upcoming-widget`) — a kind-filter tab row (All/Assignments/Exams/Readings/Other, the last grouping quiz/lab/project/manual the same way `DEADLINE_KIND_LABEL` already maps `'manual'` → `"Other"`) over a denser row layout: date block, course-colored left border (reusing the existing `courseAvatarColor()` hash), title + kind badge, course name + a relative "Due in N days"/Today/Tomorrow/Overdue label. ## 5. Context Builder

The Context Builder (PRD section 16) is a query layer over the canonical database: given a task (assignment help, exam revision, lecture summary, etc.) and a current course, it retrieves the relevant subset of resources, notes, assignments, and the course's AI profile (section 19) — it does not dump everything, and it never writes AI-inferred data back into the canonical store as fact (section 17).

### Per-course agent readiness (built 2026-08-06)

The course-detail **Readiness** tab includes an **Agent readiness** section that reports technical text availability, not comprehension, study progress, or an AI-generated judgment. `courses:getReadiness` aggregates the existing canonical state rather than adding a second readiness database:

- A resource is **readable** when its extraction status is `done` and it has at least one `document_parts` row or accepted `ocr_text`. A typed note is readable when it contains text; a handwritten note is readable once it has accepted OCR or user-entered content.
- A scanned PDF with `extraction_status = 'empty'`, or a handwritten scan with no accepted text, is **needs OCR**. The UI sends the user to the existing reviewed OCR flow rather than silently running or saving OCR.
- `pending` means extraction is still running. `failed` preserves the stored extraction error. Local failures for extractable kinds can be reset to `pending` and retried through `resources:retryExtraction`; remote failures remain tied to their next source sync rather than incorrectly passing through the local-file extractor.
- Unsupported file kinds and external Classroom links are reported separately from genuine failures. They are not silently counted as readable, but neither are external links or image/archives presented as parser errors.

The renderer shows the course total, five compact counts (Readable, Needs OCR, Pending, Failed, Other), and an unboxed issue list with the material type/source, reason, and the appropriate action. The section refreshes from `resources:extractionUpdated`, `resources:changed`, and Classroom change events, so a completed extraction or OCR save appears without navigation or relaunch. This is intentionally a deterministic local feature: Atlas does not call an LLM or infer whether the user has actually studied the material. The later reading/coverage-tracking idea remains a separate product decision.

## 6. Runtime AI integration: local MCP server

Atlas exposes its Context Builder to whichever AI coding agent the user is running via a **local MCP (Model Context Protocol) server** bundled with the app, rather than only generating static context files. MCP is itself a model/vendor-agnostic protocol — any MCP-capable client (Claude Code or others) can connect to the same server without Atlas needing to know or care which one it is.

Why MCP over static file export:

- The PRD's own goal (section 21) is that a user can start a *fresh* AI agent conversation without manually re-explaining project structure — that calls for the agent being able to query live ("what's due this week in COMP301", "pull my notes on lecture 4"), not just receive a fixed snapshot made at export time.
- The query/context-builder logic (section 16) has to exist regardless of transport. MCP is a thin protocol layer on top of that logic, not a parallel implementation.
- A static "export context to file" mode is still kept as a secondary path (same underlying query layer) for use with AI tools that don't support MCP, satisfying the PRD's AI-provider-independence goal (open question 5).

### MCP capabilities beyond text lookup

The MCP server is currently a thin transport over the same canonical query layer and exposes twelve tools. In addition to overview, course briefings, search, resource/deadline inventories, document/note reads, memory, and agent-note creation, it exposes the app's deterministic per-course readiness report and full locally-synced Classroom announcement/assignment bodies. Agent-created notes may use `course_id = NULL` for the existing General/unsorted area; those notes remain flagged `generated_by_agent = 1` and are indexed immediately.

Document-page search hits include both the `document_parts` location and the parent resource id/title/source. This is deliberately returned as navigation metadata rather than full text; the agent follows the parent id and ordinal into `atlas_read_document`.

`atlas_read_visual` is the bounded visual path. It accepts only an Atlas resource or handwritten-note id, resolves the associated local PDF/image path internally, and returns one MCP image content block. PDF pages are rendered locally with the same bundled pdfjs/canvas stack used by OCR, one page per request; small images are returned in their source bytes, and unusually large images are resized to a bounded canvas. Arbitrary filesystem paths are never accepted or returned. A missing/deleted file, external link, unsupported kind, or invalid page produces a normal error response. Atlas still makes no AI/LLM calls; the connected agent decides what the image means.

## 7. Resource Viewer: in-app preview, per file type

PRD section 10 asks for in-app viewing "whenever practical," with an external-app fallback otherwise. Implementation, per resource kind:

- **PDF, image** — PDFs are rendered locally with the bundled `pdfjs-dist` worker into Atlas-owned canvas pages, so the preview's scroll surface and styling remain under Atlas's control. Images render directly with `<img>` against a `file://` URL. The separate "Open in browser" route still streams the native PDF and therefore uses the browser's own viewer outside Atlas's styling boundary.
- **Markdown** — rendered to HTML via `marked`. Deliberately pinned to `marked@12` — v13+ dropped the CommonJS build Atlas's main process needs (it's ESM-only from v13 on), which crashes with `ERR_REQUIRE_ESM` under `require()`.
- **Text** — shown as-is.
- **DOCX** — converted to HTML via `mammoth` (pure JS, no native compile step, no Word installation needed).
- **PPTX** — **text-only** outline (each slide's text runs extracted from the raw XML inside the `.pptx` zip via `adm-zip`, XML-entity-decoded before HTML-escaping so characters like `&` round-trip correctly). There is no mature free/pure-JS library that renders real slide layout, images, or styling with good fidelity — attempting that would mean either a paid conversion API (ruled out by §0) or bundling a heavyweight rendering engine for uncertain payoff. This is a deliberate, documented scope line, not an oversight.
- **XLSX** — each sheet converted to an HTML `<table>` via `xlsx` (SheetJS), read with formula evaluation disabled (`cellFormula: false`) since Atlas only needs cell values for a read-only view. **Security note:** the `xlsx` npm package (last published 0.18.5) has known unpatched prototype-pollution/ReDoS advisories — SheetJS only ships fixed builds via their own CDN now, not npm. Originally accepted as low-risk because Atlas only ever parsed the user's own local files — that's no longer strictly true now that the Google Drive adapter (§4a) exists: an `.xlsx` dropped into the watched Drive folder by the user themselves is still "their own file," not attacker-controlled input, so the original risk acceptance still holds, but it's worth revisiting if Drive-sourced files are ever treated as less trusted than manually uploaded ones.
- **`googleapis`** (§4a) pulls in a large transitive dependency tree that includes some already-known high/critical advisories (`tar`, `glob`, `rimraf`, etc.) — these are almost entirely build/dev-tooling packages already present via `electron-builder`'s own tree (see `npm audit`), not new runtime attack surface for a local desktop app making authenticated calls to Google's own APIs. Not treated as a blocker for the same reason as the `xlsx` note above; revisit if `npm audit` ever flags something in `googleapis`'/`google-auth-library`'s actual runtime path rather than its build tooling.

### Fullscreen shortcut

Pressing **F** while the resource preview *or* the note editor is open toggles that panel's fullscreen (`toggleFullscreenPreview()`/`toggleNoteFullscreen()`), same effect as clicking its fullscreen button — added so reaching for the mouse isn't the only way to expand either. Guarded to only fire when focus isn't in a text field (`<input>`/`<textarea>`/`<select>`/`contenteditable`) — the note editor's Milkdown surface is itself a `contenteditable`, so typing a literal "f" while actually writing a note is never hijacked, same as it isn't for a deadline title or the note title field. Blurring out of the note (e.g. clicking anywhere non-editable) re-enables the shortcut for that panel.

### Opening resources in the browser

Every resource has a native right-click context menu (Electron `Menu`, not an in-page dropdown) with **"Open in browser"** — opens the resource in the user's real default browser (actual switchable tabs), not Electron's own preview panel and not a native desktop app. Backed by a small loopback-only HTTP server (`src/main/localServer.ts`, bound to `127.0.0.1` only, random port, started at app launch) at `GET /resource/:id`:

- PDF/image/text are streamed as their native content type, so the browser uses its own built-in renderer.
- Markdown/DOCX/PPTX/XLSX are rendered through the exact same conversion functions the in-app preview uses (`getPreview()` in `preview.ts`), wrapped in a minimal standalone HTML page (no Atlas stylesheet available outside the app window).
- Anything else (zip, unrecognized types) is streamed as an `application/octet-stream` download — the browser's natural behavior for content it can't render, same role the old "Open in default app" fallback played.

This deliberately replaces what used to be "Open in default app" (`shell.openPath`, which launched the OS's associated desktop application — Word, Excel, etc.) — the user specifically wanted every file type reachable from browser tabs for fast switching while working, not separate desktop windows. It also deliberately does **not** route through Google Docs/Sheets/Slides: those can only preview a file they can fetch from a public URL, so the only way to get Office files in front of them would be uploading each one to Google Drive first. That upload path is exactly what got built next, once the user made clear they actually wanted it — see below.

### Office file preview via Google Drive (built 2026-07-28, `open-questions.md` #12)

The local PPTX/DOCX/XLSX previews above stay as they are (text-only outline / mammoth HTML / SheetJS tables, all instant and fully offline) — this is an *additional* action for when real slide/document layout is wanted, not a replacement.

**Why this exists, and why it was initially deferred.** The first time the user asked about this, the recommendation was to hold off — reasoning that it contradicted the local-first design (§2), that reconnecting Drive after an OAuth scope change was a real cost, that a local desktop-app fallback existed, and that Slides conversion fidelity wasn't good enough to be worth it. Directly asking the user surfaced that three of those four assumptions were simply wrong for their actual situation: they're not opposed to files leaving the machine if it means better viewing, they have no Word/PowerPoint installed (so "open the desktop app" isn't a real option), and the low bar of the current text-only outline means almost any improvement clears it. The fourth point (fidelity) turned out to be moot once the approach changed from *converting* to Slides/Docs (which does lose fidelity) to just letting Drive preview the original Office file directly (which doesn't).

**OAuth scope**: Drive's connection (§4a) gained `drive.file` alongside its existing `drive.readonly` — this only grants access to files Atlas itself creates via the API (the uploaded preview copies below), which Google classifies as *non-sensitive*, a narrower grant than `drive.readonly` despite being an addition. Per the standing scope-change gotcha (§4b), an already-issued refresh token doesn't retroactively gain a new scope — the user has to disconnect and reconnect Drive once after this shipped.

**A dedicated, Atlas-owned folder, with one subfolder per course** ("Atlas Previews", `google_drive_preview_folder_id` in `app_settings`; each course's own subfolder inside it, named after the course, `courses.drive_preview_folder_id`) — created automatically on first use, separate from the user-designated inbox folder (§4a) which serves a completely different purpose (files coming *in*, not going *out*). The per-course subfolder isn't just tidiness: several courses' files can share an identical original filename (e.g. every course's own seeded `lecture-slides.pptx` in this project's test data), which would otherwise be indistinguishable from each other sitting flat in one folder. `ensureFolder()` (`googleDrive.ts`, shared by both the root folder and every course subfolder) re-verifies a remembered folder still exists (not trashed) before reusing it, recreating it if the user ever deletes it by hand in Drive, rather than every subsequent upload failing with a confusing "not found."

**Upload once, cached thereafter** — the single most important part of making this pleasant to use, not just possible. `resources.drive_preview_file_id` plus the local file's `drive_preview_synced_size`/`drive_preview_synced_mtime_ms` (its `fs.stat()` values at the moment of the last successful upload) are stored per resource. A later request for the same resource compares the current stat against those — an exact match skips the network entirely and reuses the existing Drive file's URL; any difference triggers a re-upload **in place** (`drive.files.update`, keeping the same Drive file ID) rather than creating a second copy and orphaning the first. This means only the very first open of a given file is ever slow.

**Large files aren't special-cased.** The upload body is a readable stream (`fs.createReadStream`), not a buffered read — `googleapis`/`gaxios` switches to a resumable upload automatically once the payload is large enough to need one, so a multi-hundred-MB lecture deck doesn't need different handling than a small handout.

**No byte-level progress reported.** The `googleapis` client's `onUploadProgress` hook is marked deprecated/non-functional in the version this project is pinned to — rather than wiring up a progress bar that would never actually move, the renderer just shows an indeterminate "Uploading…" between upload start and completion (`resources:driveOpenStart`/`Success`/`Error` events from `main.ts`).

**Entry points**: a resource's right-click context menu gains "Open in Google Drive" (main-process click handler calls the upload/open logic directly, no IPC round-trip needed since the menu itself lives in the main process), and the in-app preview modal gains an equivalent button. Local `pdf`, `image`, `pptx`, `docx`, and `xlsx` resources can be uploaded to the Atlas-owned preview folder; PDFs/images are included because Drive can open them and the user explicitly wants that route available even when Atlas already has a local preview. Classroom/link resources are different: their stored external URL opens directly in the browser and is never uploaded as a local Drive preview. Opening uploaded files hands off to `shell.openExternal` with Drive's standard `https://drive.google.com/file/d/<id>/view` URL, same as every other "open externally" action in Atlas.

**Cleanup.** Deleting a resource (or a whole course, which cascade-deletes its resources) also deletes that resource's uploaded Drive copy — best-effort and never awaited, since a stray leftover file in the preview folder is a cosmetic annoyance, not a data-loss risk, and must never block or fail the actual local delete. A Settings action ("Clear Drive preview cache," `Settings > Sources`) deletes every uploaded copy and forgets them locally in one go, for reclaiming Drive space or recovering from anything gone stale.

**Known caveat, not solved by this feature: multiple signed-in Google accounts.** Drive is connected against the user's *personal* account, while Classroom is connected against their *college* account (§4b) — both can be signed into the same browser simultaneously. When `shell.openExternal` hands the browser a Drive link, the browser opens it as whichever Google account it currently treats as active, which may not be the personal account the file actually lives in — producing a confusing "you need access" page instead of the file, even though the upload itself succeeded. Google's own workaround is an account-index segment in the URL (`/u/0/`, `/u/1/`, …), which Atlas has no reliable way to determine automatically. Not fixed in this pass; if it turns out to be a recurring problem in practice, the options are asking the user to set their personal account as the browser's default identity, or having Atlas remember which account-index number to append per connection.

**Scope note**: Drive preview now covers PDFs, common images, and Office Open XML (`.pptx`/`.docx`/`.xlsx`). The existing extension mapping labels legacy `.ppt`/`.doc`/`.xls` files with the corresponding Office kind, but their older binary contents may still fail the OOXML readers; they are not claimed as newly supported here. Plain-text formats such as `.csv`, `.tsv`, `.json`, `.xml`, `.html`, `.rtf`, and common configuration/log files are readable in Atlas as text but are not copied to Drive by this action. Archives, media files, unknown extensions, malformed files, and Google-native Classroom items that cannot be exported remain unsupported in the relevant local/remote extraction path.

**Not covered by `scripts/verify-app.js`** — same limitation as the rest of the Drive/Classroom integration (needs a live Google account and real upload/view round-trip); verify manually against the user's real Drive account instead.

## 8. Notes: Markdown, flat per course, live-rendering editor

Format and organization are both resolved — see `open-questions.md` #1 for the full reasoning. Summary:

- **Format: Markdown**, not rich text. The deciding factor was AI-agent integration, not editing convenience: rich text (HTML or a JSON doc tree) would just get flattened to something markdown-like before an AI agent could use it anyway, so storing markdown from the start avoids a lossy round-trip and keeps notes trivially indexable by the existing FTS5 `search_index` table. `notes.content_markdown` (schema already had this column from Phase 0).
- **Organization: flat per course, no folders/subfolders.** The user's prior Notion workflow was structurally "semester > course > session-titled note" (e.g. "W1L1", "W1L2") — Atlas already provides the semester (see below) and course layers, so a note just needs a user-given title, not a second manually-maintained folder tree inside each course.
- **Editor: Milkdown, via the `@milkdown/crepe` preset** (MIT) — typing `#`, `-`/`*`, `1.`, `---`, etc. converts live to real headings/lists/dividers, matching the Notion/Obsidian feel the user asked for. **Toast UI Editor was tried first and replaced** after the user reported it felt "raw and unpolished": its WYSIWYG mode doesn't actually support typing markdown shortcuts to create lists (typing `- ` just inserted the literal characters), and its toolbar never shows an active/highlighted state for the current selection (pressing Ctrl+B bolded text but gave no visual feedback that Bold was now active). Both were confirmed as real gaps via hands-on browser testing, not assumed — and both are core to how the user actually works (bullet-heavy notes, frequent formatting). Crepe was verified to handle all of them correctly (live list/heading/divider shortcuts, Tab/Shift+Tab nesting, a floating selection toolbar with correct active-state highlighting) before switching, plus it bundles KaTeX math rendering out of the box, which Toast UI Editor has no equivalent for and the user needs for academic notes (formulas, complexity notation). Uses the official `frame-dark` theme to match Atlas's UI. Content autosaves 600ms after the last edit via Crepe's `markdownUpdated` listener (debounced) and flushes immediately on close.
- Milkdown's own dependencies (ProseMirror, CodeMirror for code blocks, KaTeX for math, a small internal Vue instance for its math/table block editors) are resolved and bundled by esbuild along with their CSS/webfont assets (`scripts/build-renderer.js` — needs `file` loaders for KaTeX's `.woff`/`.woff2`/`.ttf`, and emits a sibling `renderer.css` that `index.html` links directly).
- **The database is notes' real, live source of truth — but every save also mirrors the note out to a plain `.md` file**, at `files/<course>/notes/<title>.md` (`exportNoteToFile()` in `main.ts`). This resolves a real gap the user hit: with content living only in `notes.content_markdown`, there was no way to get a note out of Atlas for external use (grep, copy elsewhere, hand to another tool) — the on-disk-file-per-course design was supposed to be the "user can browse/use their stuff" layer (§2), and notes were the one thing that broke that promise.
  - **Strictly one-way.** Atlas never reads this file back — editing it externally just gets silently overwritten the next time the note is saved from within Atlas. Two-way sync (watching the file, merging external edits, resolving conflicts with the live DB copy) was considered and explicitly declined by the user as unneeded complexity for what's fundamentally an export, not a second editing surface.
  - **Renaming a note renames its export.** The exported filename is derived from the note's title (sanitized, collision-disambiguated the same way as resources); `notes.exported_path` tracks the last-written path so a title change can find and remove the stale file (and its assets folder, below) rather than leaving orphans behind.
  - **Embedded images are linked, not copied** — the note's local-server image URL is rewritten to a relative path pointing straight back at the single real file in that course's own `files/<course>/notes/note-images/` folder (e.g. `note-images/<uuid>.png`), not a per-note duplicate. First shipped as a per-note copy in a `<title>.assets/` folder; the user noticed the same image existing twice on disk and asked whether one file could serve both jobs. It can: a relative link resolves standalone in any markdown viewer exactly like a copy would, and since the image lives right alongside the exported `.md` inside the same course's `notes/` folder, the whole folder travels together — the one thing lost versus a copy is that moving a *single* exported note file out on its own, without the rest of `notes/`, would leave a broken link. Accepted trade-off, chosen over the disk-space duplication. The in-app editor and read-only browser view are unaffected — they still use the live local-server URL. (Originally a single flat `Atlas-Storage/note-images/` folder shared across all courses; moved to per-course storage per the user's explicit request — see the image storage location note below.)
  - **Excluded from the managed-storage watcher.** Every course's `files/<course>/` folder is already watched to auto-import manually-added files as resources (§4) — without an exclusion, Atlas's own exported `.md`/`.assets` files would get picked up by that watcher and re-imported as bogus resources. Both the `add` and `unlink` handlers skip anything under the course's `notes/` subfolder.
- **Fonts are forced sans-serif** — Crepe's default theme uses a serif font for headings/quotes, which looked inconsistent against the rest of Atlas's sans-serif UI; overridden in `styles.css` scoped to `.milkdown` elements.
- **Title auto-follows the first line, Google-Docs style** (`notes.title_is_manual`, defaults to 0): every autosave derives a title from the note's first non-empty line (stripping heading/list/quote markup, inline emphasis like `**bold**`/`_italic_`/`` `code` ``, and skipping a line that's only an image — the image URL/alt text isn't meaningful title material, and turning it into one produced a genuinely broken export filename during development) and updates `title` — unless the user has ever edited the title field directly, which flips `title_is_manual` to 1 permanently for that note and decouples it from content from then on. A blur on an unchanged title field doesn't count as an edit, so merely clicking into the title and clicking away doesn't accidentally lock it.
- **Notes follow the same shared list/icon view toggle as resources** — no separate toggle, `renderNotes()` just reads the same app-wide `viewMode` setting resources already use, per the user's request that view mode be one consistent, standardized preference across the whole app rather than per-section.
- **"Open in browser" for notes is read-only**, unlike the WYSIWYG editor in the app. An editable browser copy would mean two live editing surfaces writing to the same note with no conflict resolution between them (the desktop Crepe instance and the browser tab); read-only sidesteps that entirely and matches the same "reference alongside other tabs" role the feature already plays for resources. Rendered via `marked`, with `$...$`/`$$...$$` math segments extracted and rendered through KaTeX (`katex.renderToString`) before the markdown pass, then spliced back in — `marked` has no native concept of math syntax. KaTeX's CSS/webfonts are served from two additional local-server routes (`/katex.css`, `/katex-fonts/:file`) rather than inlined, since the external browser tab has no access to Atlas's own bundled assets.
- **Slash-menu shorthand** (typing `/h1` then Tab to jump straight to Heading 1) isn't supported by Crepe's slash menu as shipped — its filter does substring matching against the full visible label ("Heading 1"), not fuzzy/alias matching, so `h1` (no space) matches nothing and the menu just closes. Investigated rather than assumed working. Not worth building a workaround for: the equivalent live markdown shortcut (typing `# ` for H1, `## ` for H2, etc., directly in the text — no menu at all) already works and is arguably faster than the slash-menu path the user described.
- **Heading labels in the slash menu are "H1"–"H6"**, not "Heading 1"–"Heading 6" — configured via Crepe's `BlockEdit` feature config (`textGroup.h1.label`, etc.), per the user's ask for something shorter/more scan-friendly.
- **Headings are bold by default, and Ctrl+B still toggles it off** — a real trade-off, not a simple CSS tweak. Crepe's own theme renders headings at `font-weight: 400` (size differs by level, weight doesn't), which read as visually flat. Forcing `font-weight: 700` on `h1`–`h6` via CSS alone would satisfy "bold by default" but make Ctrl+B a no-op *inside* a heading, since the CSS weight would always win regardless of whether the underlying `strong` mark is present — the two asks are in tension unless the boldness comes from a real, togglable mark rather than fixed CSS. Implemented as a small custom ProseMirror plugin (`$prose` from `@milkdown/kit/utils`, registered via `crepe.editor.use(...)` before `.create()`) with an `appendTransaction` hook: whenever the cursor sits inside an *empty* heading (freshly created, or emptied back out), it primes ProseMirror's `storedMarks` with `strong` so the next character typed comes out bold automatically — the same mechanism as clicking a Bold button then typing. Once real text exists in the heading, the plugin stops touching it, so it never fights a manual Ctrl+B afterward. Verified via both entry paths (typing `# ` and picking H1/H2 from the slash menu), toggling off and back on, and confirming plain paragraphs are unaffected.
- **Images embedded in note content are saved to a stable, Atlas-owned location**, not left as the `blob:` URL Crepe's image block defaults to. A `blob:` URL only lives as long as the renderer process that created it — dead on every app restart, and never resolvable from the read-only browser view (a separate process/origin entirely) either. `notes:saveImage` (main.ts) copies the uploaded file's bytes into that course's own `files/<course>/notes/note-images/<uuid>.<ext>` folder (per-course, not a flat cross-course store — see below) and returns a URL served by the local HTTP server, wired into Crepe's `ImageBlock` feature (`onUpload`/`inlineOnUpload`/`blockOnUpload`) instead of the default. The URL now carries the course id (`/note-image/:courseId/:filename`) so the server can resolve which course's folder to read from at request time. Orphaned image files aren't cleaned up when a note is deleted — a known, accepted gap for now, not something to silently "fix" by guessing at retention rules.
  - **Per-course, not a shared flat folder.** Originally all note images lived in one flat `Downloads/Atlas-Storage/note-images/` folder regardless of course, on the reasoning that a note referencing an image is what ties it to a course, not the image's location on disk. The user explicitly disliked this and asked for images to live under `Atlas-Storage/<course>/notes/note-images/` instead, matching where the exported `.md` file itself lives — `getNoteImagesDir()` (`paths.ts`) now takes the course's folder name and nests under that course's `notes/` subfolder. This also simplified the exported `.md`'s image link from a `../../../note-images/...` reach-up to the shared store down to a same-folder `note-images/...` relative path. One existing real note image was migrated by hand into its course folder as part of this change (moved the file, rewrote the DB's stored URL and the already-exported `.md`'s relative link).
- **The local HTTP server uses a fixed port (`47823`), not an ephemeral one.** This was a real bug caught during development: `server.listen(0, ...)` picks a random free port each launch, and since note images bake that server's URL directly into `content_markdown` (persisted in the database), a previously-inserted image would 404 the moment the app restarted with a different port — confirmed via an actual restart test before landing on the fix. "Open in browser" URLs for resources/notes don't have this problem since they're generated fresh on demand and never persisted; only note images needed a stable port. Falls back to an ephemeral port only if the fixed one is somehow already taken (rare on a single-user desktop app), accepting that any already-saved image references won't resolve for that one session.

### Semester filter

Courses already carried a `term` field (the fixed Monsoon/Spring dropdown). A course-list filter (`#semester-filter`) was added alongside the notes work, at the user's request, to scope the visible course list to one semester at a time — client-side filtering over the existing `courses.term` column, no schema change. The selection is a persisted `app_settings` entry (same mechanism as the view-mode setting, §2), so it survives a relaunch rather than resetting to "all" every time.

## 9. Global search (SQLite FTS5)

A single search box in the header (`#search-input`) queries across every course at once — notes, resources, announcements, and assignments — rather than being scoped to whatever course happens to be open, since the point of search is finding something without first remembering which course it's in.

- **Index maintenance: targeted updates with a rebuild repair path.** Ordinary course, resource, note, announcement, and assignment mutations update only their affected `search_index` rows. A full `rebuildSearchIndex()` remains available for repair/backfill batches and is run at launch only when the source/index counts show that something changed while Atlas was closed. This keeps the index correct without making every local mutation or launch pay for a full-table delete and reinsert.
- **What gets indexed as body text.** Notes index their full `content_markdown`, OCR-accepted note text is included, and extracted PDF/DOCX/PPTX/XLSX content is stored and indexed as page/section parts. Resource and note names remain searchable independently from in-file content, while Classroom announcements and assignments are indexed as their own result group. The shared query layer is used by the app, static export, and MCP server so search behavior does not drift between clients.
- **Query syntax is quote-and-prefix per word, not raw FTS5 syntax.** User input is split on whitespace, each word individually double-quoted and prefix-matched (`toFtsQuery()` in `contextBuilder.ts`), e.g. `data str` becomes `"data"* "str"*`. This gives predictable per-word prefix matching without exposing FTS5's own query grammar to the search box. It is deliberately not natural-language intent resolution: an external agent must treat a specific numbered request as unresolved until the resource title and course context are verified, following `MCP_AGENT_GUIDE.md`.
- **Results are ranked by FTS5's built-in `rank`** (`ORDER BY rank`, ok since search columns aren't `UNINDEXED`) and capped at 30, joined against `courses` to show which course each result belongs to. `snippet()` generates a highlighted excerpt around the match; the main process wraps matched terms in literal `<mark>`/`</mark>` text, and the renderer escapes the rest of the snippet as HTML before turning just those two literal marker strings back into real tags (`highlightSnippet()` in `renderer.ts`) — since a note/resource body is user-authored text that could otherwise itself contain `<`/`>`/`&`, this keeps it from being interpreted as markup when dropped into the results dropdown via `innerHTML`.
- **Clicking a result navigates there directly**, not just to the course: `openSearchResult()` selects the result's course, then fetches that course's notes/resources and opens the matching one in the existing note editor or resource preview overlay — the same code paths as clicking it from the course's own list, no separate "search result view."
- Debounced 250ms after the last keystroke, closes on Escape or a click outside the search box, and shows an explicit "No matches" state (rather than an empty or hidden dropdown) so an unproductive search doesn't look like search silently did nothing.
- **Keyboard-navigable, not mouse-only** — Arrow Down/Up move an `.active` highlight through the results (mouse hover sets it too, so the two stay in sync rather than fighting each other), and Enter opens whichever result is active, defaulting to the top result if the user hasn't arrowed to one yet. Added per the user's explicit preference to minimize mouse use wherever reasonable.
- **Ctrl+L jumps to search from anywhere**, matching a browser's address-bar shortcut convention (the user's own point of reference) — focuses `#search-input` and selects any existing text so typing immediately replaces it, same as a browser does. Deliberately not surfaced anywhere in the UI (no tooltip/hint) per the user's explicit request to keep the interface uncluttered.

## 10. Deadlines: one unified per-course timeline, not a separate Assignments tab

Per-course "Deadlines" section (`#deadlines-section`) — title, kind, optional due date/time, optional description, complete/incomplete — backed by the `deadlines` table that already existed in the schema (extended with a `description` column).

- **No separate "Assignments" tab built**, even though PRD §8 lists Assignments and Deadlines as distinct course-workspace tabs, and the schema has a distinct `assignments` table (title/description/status: open/submitted/graded). Asked the user directly, since a manually-added "Homework 3 due Friday" could plausibly go in either one with no sync built yet — they chose Deadlines only. `deadlines.kind` already includes `'assignment'` as one of its values (alongside reading/quiz/lab/project/exam/manual), so a manual assignment due date is already representable there; the `assignments` table's real purpose is holding synced Google Classroom data in Phase 3, where the description/status fields actually matter. See `open-questions.md` #13.
- **Sort order: incomplete first, then soonest due date, with no-due-date items last within each group** (`ORDER BY completed ASC, (due_at IS NULL) ASC, due_at ASC`) — surfaces what's actually actionable (not yet done, coming up soonest) at the top, rather than plain chronological or creation order. Works unmodified whether or not a due date carries a time — see below — because the two string formats still compare correctly lexicographically (a same-day entry with no time sorts before one with a time, which reads naturally as "unspecified time = start of day").
- **Due date/time: `due_at` holds either `'YYYY-MM-DD'` or `'YYYY-MM-DDTHH:MM'`**, the time component being optional per the user's request ("add a time as well, make it optional") rather than a schema-mandated second column always present but often unused. Parsed back out with explicit year/month/day/hour/minute components (`splitDueAt()`/`formatDueDate()` in `renderer.ts`), not `new Date(str)` directly, to avoid the browser interpreting a bare date string as UTC midnight and displaying the day before in negative-UTC-offset timezones.
- **The due date can be typed (`dd-mm-yyyy`) or picked from a calendar — both, not one or the other**, per explicit request. The visible field is a plain text input; a hidden native `<input type="date">` backs a 📅 button that calls the input's `showPicker()` (Chromium 99+, available in Electron) and syncs its picked value back into the typed field (and vice versa, so reopening the picker after typing a date shows that date, not blank). `typedDateToIso()`/`isoDateToTyped()` in `renderer.ts` convert between the two formats.
- **"Today"/"Tomorrow" replace the date for near-term deadlines** — read faster at a glance than a date the user has to mentally compare against today. Anything from the day after tomorrow onward falls back to a plain formatted date, where a relative label stops being obviously faster to parse. The time (if set) is always appended regardless — e.g. "Today at 2:30 PM".
- **Deadlines share the app-wide list/icon view toggle** with resources/notes (no separate per-section toggle, consistent with how that toggle was already designed to be one app-wide preference — see the Semester filter/view-mode section above). Icon view gives each `kind` its own emoji (`DEADLINE_KIND_ICON` in `renderer.ts`) so a course's deadlines are visually scannable by type.
- **Editing an existing deadline reuses the same modal as adding a new one** (`#deadline-editor-overlay`), toggled between a read-only "view" mode (rendered description, clickable mentions, an Edit button) and a form "edit" mode — rather than two separate overlays, since a deadline is little enough content that one panel with a mode switch is simpler. Clicking a deadline row/tile opens the view mode; there is no dedicated "Edit" menu item since the row click already gets you there, matching how notes/resources already work (click a row to open the thing).
- **Optional free-text description, supporting `@`-mention references to the course's own resources/notes** — modeled on Claude Code's own `@file` reference convention, which the user pointed to directly. Typing `@` in the description textarea opens an autocomplete filtered against that course's resources and notes (`mentionCandidates`, loaded from `listResources`/`listNotes` when the editor opens — not the whole filesystem, since resources/notes are the things Atlas already tracks and can navigate back to). **Keyboard-navigable, not mouse-only** — Arrow Up/Down move an `.active` highlight through the suggestions (mouse hover sets it too, same pattern as the global search results dropdown), Enter inserts whichever is active or the top match if none has been arrowed to yet, Escape dismisses the list without closing the whole editor. Selecting one inserts a token in the stored text, `@[Title](resource:<id>)` or `@[Title](note:<id>)` — plain, grep-able markup, not an opaque ID a human reading the raw description couldn't make sense of. Rendered read-only (`renderDeadlineDescription()`), the description is HTML-escaped first (it's user-authored text that could otherwise contain `<`/`>`/`&`) and only the token pattern — which survives escaping untouched, since escaping doesn't touch `[`/`]`/`(`/`)`/`:` — is turned into a real, clickable link; clicking it selects the deadline's course and opens the referenced resource/note in the same preview/editor UI used everywhere else.
- **Completing a deadline is a checkbox, not a delete** — completed items stay visible (struck through, sorted to the bottom) rather than disappearing, so there's still a record of what was due and done. Available directly on each list/icon row (no need to open the viewer just to check something off). Deleting is the same native right-click → confirm pattern as every other list in the app (resources, notes, watched folders).
- Not wired into global search (`search_index`) — deadlines are a todo-style overwrite-in-place list, not the kind of longform content (notes, resource files) search is meant to help you re-find.

## 11. Dashboard v1 (PRD §13)

A `#dashboard-section` above the course list — global across every course, not scoped to whichever one is currently selected/open, since the whole point of a homepage overview is not having to open each course individually to know what's going on. Three widgets, the exact set `ROADMAP.md` scoped for v1 (announcements/assignments widgets are v2, deferred until those have real data behind them — see `open-questions.md` #13):

- **My courses** — every non-archived course with a colored initial-letter avatar and its resource count (`dashboard:courseSummaries` in `main.ts`, a `COUNT(*)` subquery per course). Clicking one selects that course and scrolls to the Courses section, same as clicking it in the course list itself. Added as part of the session-33 UI reskin (§12) — the mockup the user was working from had a "My Courses" card, and it was a natural fourth widget alongside the three already here.
- **Upcoming deadlines** — incomplete deadlines with an actual due date, across every course, soonest first, capped at 8 (`dashboard:upcomingDeadlines` in `main.ts`). A no-due-date deadline is deliberately excluded here even though the per-course Deadlines list shows it (sorted last) — "upcoming" implies a timeline, and a dateless entry has nothing to contribute to one.
- **Recently added resources** — the 8 most recently added resources across every course (`dashboard:recentResources`), regardless of which course they belong to.
- **What changed today** — a combined feed of resources added and notes updated, filtered to the user's *local* calendar day. `dashboard:recentActivity` deliberately does the "is this today" comparison in the renderer (`isTodayLocal()`), not in SQL — a server-side `date('now')` comparison would use UTC's day boundary, which can disagree with the user's actual local "today" depending on timezone and time of day (the same class of bug the note-timestamp/deadline-date code elsewhere in this doc already had to account for). The main process just returns a generously-sized recent feed (15 resources + 15 notes, timestamp-sorted); the renderer filters and caps display to 20.
- **Refresh strategy: fire-and-forget from the three per-course render functions**, not a dedicated hook at every resource/note/deadline mutation call site. `renderResources()`, `renderNotes()`, and `renderDeadlines()` already run after every mutation that could affect the dashboard (upload, delete, note save, deadline create/edit/complete, across every one of their several call sites); each now also kicks off `renderDashboard()` without awaiting it, since the dashboard is a secondary overview widget, not the thing whatever action the user just took is waiting on. Simpler than instrumenting each mutation site individually, same reasoning as the search-index full-rebuild approach (§9).
- **Clicking any dashboard item navigates directly to it** — selects that item's course, then opens the resource/note/deadline in the same preview/editor/viewer UI already used everywhere else in the app (`openDashboardDeadline()`/`openDashboardResource()`/`openDashboardActivityItem()` in `renderer.ts`), the same pattern global search results and description mentions already use.
- **A small `•` separates the course name from the due/changed date-time** in the deadlines and activity widgets (`.dashboard-item-meta::before`) — without it, e.g. "Data Structures & Algorithms Tomorrow at 23:45" reads as one run-on clause at a glance. The "recently added resources" widget has no such separator since it has no trailing date-time to separate from the course name.
- **What "what changed today" actually covers**: only resources *added* today and notes *updated* today (`dashboard:recentActivity`). It does not include resource deletions, or deadlines added/edited/completed — resources have no in-place "edit" concept (they're static uploaded files), and deadlines aren't timestamped with a created/updated column at all currently.

## 12. UI reskin: sidebar shell, real page routing, theme system

The user asked for a visual reskin inspired by mockups they shared. This went through several rounds of hands-on feedback rather than landing right the first time — a scroll-shortcut sidebar, then a docked-pane preview layout, both tried and then replaced after the user pointed out real problems with each. This section describes the version actually shipped after all of that, not the intermediate attempts.

Scope stayed bounded to a reskin/restructure of what already exists, not new product concepts: no Tags, Trash, or Notifications, and no separate Assignments concept (the separate `assignments` table is used for synced Classroom data). The early UI iteration intentionally excluded Calendar and Settings while they had no usable content; both were later restored as real surfaces once Calendar data, source connections, theme controls, storage, agent access, and About content existed. The current sidebar pages are Dashboard, Courses, Resources, Notes, Calendar, and Settings.

*(Both exclusions above were revisited once there was real content to justify them — a Calendar page and sidebar entry shipped in §4d, and Settings came back in session 46's UI-polish batch, `open-questions.md` #22, once Drive/Classroom connections plus a real theme picker gave it actual content instead of one static line.)*

### Real page routing, not a scroll shortcut

`showPage(page)` in `renderer.ts` hides every `.app-page` section except the one matching `#page-<name>` and marks the corresponding sidebar button `.active` — genuine mutual-exclusion visibility, not `scrollIntoView`. The six sidebar pages are **Dashboard**, **Courses**, **Resources**, **Notes**, **Calendar**, and **Settings**. "Search" isn't a sidebar item or a page — it lives only in the top bar (`focusSearch()`, also reachable via Ctrl+L from anywhere), since a sidebar entry for something already visible at the top of every page was redundant and read as a second, competing search affordance.

- **Courses page** shows *only* the course grid — no other feature's content appears on it. Clicking a course card navigates to a genuinely separate detail view (`#courses-detail-view`, toggled via `showCourseListView()`/`showCourseDetailView()` in `renderer.ts`, with its own "← Back to Courses" control), not an inline drill-down appended below the still-visible grid — the first version did the latter and the user explicitly asked for real navigation instead. The detail view shows that course's **Deadlines** and **Watched folders**, plus (once Classroom-linked) **Announcements/Assignments/Classwork**, plus two small link buttons ("N Resources" / "N Notes") that jump to the Resources/Notes pages pre-filtered to this course rather than duplicating their list UI inline. *(Originally all of this was one long scrolling page — session 46's UI-polish batch, `open-questions.md` #22, rebuilt it as tabs once enough sections had accumulated that scrolling became the user's main complaint; see that entry for the tab mechanics.)*
- **Resources page** — global, every resource across every course. Left rail lists courses (click to filter) plus kind-filter chips (All/PDF/Document/Image/Presentation/Spreadsheet/Other, mapped from Atlas's actual `kind` values). The list (`#all-resources-list`) takes the rest of the page width. Clicking a resource opens a **full overlay modal** (`#preview-overlay`/`#preview-panel`) — a docked inline pane was tried first, but left too little width for the list next to it for what the content actually needed, so it was reverted back to a modal. Uploading opens a small **course-picker popup** (`pickCourse()` in `renderer.ts`, anchored under the "Upload file" button) rather than a permanent `<select>` sitting in the page header, which the user found confusing (it looked like a second course filter alongside the rail).
- **Notes page** — global, every note across every course, grouped by recency (**Today / This week / Older**) in a left column, with its own course rail (same component as Resources', `renderCourseRail()`) for filtering by subject. Opening a note shows a **global overlay modal** (`#note-overlay`), same as the Resources preview — originally this was a docked inline pane, since an earlier round's complaint about wasted space was specifically about the Resources preview, not Notes; converted to an overlay in session 37 once opening a note from Dashboard/course-detail needed to not navigate pages first (see "Open in place, never redirect" below). "+ New note" uses the same course-picker popup as Resources' upload button.
- Backend listings behind the two global pages: `resources:listAll`/`notes:listAll` (main.ts) — plain joins against `courses` for the display name, parallel to the existing `resources:listByCourse`/`notes:listByCourse` which course-scoped callers (deadline mentions, the course detail view) still use.

### Grid/List, not List/Icons — one naming convention everywhere

Courses, Resources, and Deadlines each have a two-way view toggle. Courses called it "Grid/List" from the start; Resources/Deadlines originally called the same concept "List/Icons" — the user asked for one consistent name. The underlying `viewMode` preference (`renderer.ts`) is now typed `'list' | 'grid'` throughout (was `'list' | 'icons'`; a saved `'icons'` value from before the rename is still honored on read, so an existing preference isn't silently reset), and every toggle button pair is icon-only (monochrome SVG, no text label) rather than mixing text buttons (Courses) with text buttons using different words (Resources/Deadlines).

### Full-window fullscreen, not "collapse the columns next to it"

The Resources preview modal's fullscreen toggle (`toggleFullscreenPreview()`) now expands `#preview-overlay` to cover the whole window (`.fullscreen` class) — the intermediate docked-pane version's "fullscreen" only hid the sibling rail/list columns without the pane itself growing to fill the freed space, which is exactly why the user reported "the fullscreen keybind doesn't do anything." The Notes editor's docked-pane fullscreen had a related but distinct bug: `#notes-split`'s own `grid-template-columns` rule is an ID selector and was silently outranking the `.pane-fullscreen` class rule that was supposed to collapse it to one column, so the editor pane visibly shifted right into a still-reserved second column instead of actually filling the width. Fixed with a more specific `#notes-split.pane-fullscreen` rule — the same "an ID selector wins regardless of which rule comes later" lesson behind the recurring `[hidden]` bug below, just applied to a different property.

### Courses page: card grid, not a plain list

`renderCourses()` renders `li.course-card` cards (colored avatar, name, code, a "⋯" button that opens the same native context menu right-click already did, and a resource/deadline count row from `dashboard:courseSummaries`) into a CSS grid (`ul#course-list.view-grid`), with `view-list` as a flat-row alternative. **"+ Add course" is a rare action** (a handful of courses per semester, then done) so the create form (`#course-form`) is hidden by default behind an explicit toggle button rather than permanently occupying page space.

### Sidebar collapse and window state

The sidebar can collapse to an icon-only rail (`#sidebar-collapse-toggle`, bottom of the nav column, chevron flips direction) — persisted via `app_settings` like every other view preference, so it stays collapsed (or not) across a relaunch. Separately, the whole window's size/position/maximized state is now remembered too (`loadWindowState()`/`saveWindowState()` in `main.ts`, persisted as a JSON blob under `app_settings` key `windowState`, restored via `getNormalBounds()` so a maximized window's *un-maximized* size is what comes back if it's ever un-maximized) — first run with no saved state defaults to maximized, matching the user's request that the app not always reopen at a fixed 1280×800.

### Dashboard: a stat strip, plus one widget promoted to cards

The dashboard's four list widgets (My courses / Upcoming deadlines / Recently added resources / What changed today) read as "empty" whenever any one list was short, regardless of how much real data existed elsewhere in the app. Two changes: a **stat strip** above the widgets (`dashboard:stats` IPC handler — total courses/resources/notes, plus upcoming-deadline count) gives the top of the page real visual weight unconditionally, and **"My courses" was pulled out of the four-widget grid** into its own full-width row rendered as a wrapping row of colored chip-cards (avatar + name + code + resource count) rather than a plain vertical list — a course has a real visual identity (color, initial) that a resource/deadline/activity row doesn't, so it's the one widget naturally suited to card treatment.

### Theme system

A fixed set of ~13 CSS custom properties, not a duplicated ruleset per theme. Every surface/border/text color in `styles.css` traces back to one of `--color-bg`, `--color-bg-elevated`, `--color-bg-elevated-2`, `--color-border`, `--color-border-soft`, `--color-hover-bg`, `--color-text`, `--color-text-muted`, `--color-text-secondary`, `--color-text-body`, `--color-text-dim`, `--color-accent`, `--color-canvas`, defined once on `:root` (dark, the historical default) and overridden on `:root[data-theme='light']`. The fixed amber accent is applied by `applyTheme()` in `renderer.ts`; the user-facing theme controls live in Settings → Appearance and persist through `app_settings`.

The note editor's Milkdown surface genuinely follows the theme: Crepe's `frame`/`frame-dark` theme files turned out to be nothing but `--crepe-*` custom properties scoped to `.milkdown` (confirmed by reading the actual files in `node_modules`, not assumed), so both variable sets are inlined directly in `styles.css`, gated by the same `:root[data-theme='light']` selector the rest of the app uses — no runtime CSS-swapping infrastructure needed, and no permanently-dark editor surface sitting inside an otherwise-light app.

### Recurring `[hidden]`-vs-own-selector bug — several fresh instances this round

Documented in `CLAUDE.md` as a standing check, and still worth calling out how often it recurs: an element toggled via `el.hidden` must never have `display` set unconditionally on its own selector (ID *or* class), because that rule outranks the browser's default `[hidden] { display: none }` regardless of specificity — author-stylesheet rules always beat user-agent ones. Hit again this round on `.split-preview` and `form#course-form` (fixed with `:not([hidden])` scoping, same as every prior instance), plus the related-but-distinct `#notes-split.pane-fullscreen` specificity bug described above.

### A real, unrelated bug found and fixed while investigating a UI complaint

The user asked "why does one course show resource/deadline counts and the other doesn't" — investigation (via a throwaway Playwright script measuring `getBoundingClientRect()` against the user's real data) found a stale CSS rule, `ul#course-list li { display: flex; ... }`, left over from before the course-card grid was built. Because it's an ID selector, it silently outranked `li.course-card`'s own (class-only) layout rule, turning every card into a flex row instead of a stacked column — the counts row got squeezed into a narrow strip pushed past the card's right edge and clipped by `overflow: hidden`, visible or not depending on exact content width. Fixed by deleting the stale rule (the flat-list layout it was written for no longer exists — every `#course-list` item is a `.course-card` now) and consolidating the `.selected` outline into one rule that covers both grid and list view.

### A real modal for the course picker, plus drag-and-drop upload

A follow-up round of feedback pointed out that the small anchored course-picker popup (`pickCourse()`) cut off past the screen edge once there were more than a couple of courses — genuinely unusable with a realistic course list. Replaced with `#course-picker-overlay`, a proper modal with a search box (`renderCoursePickerList()` filters as you type) shared between the Upload and New Note flows via a `mode` parameter.

Upload additionally gets a drag-and-drop zone inside the modal (`#course-picker-dropzone`, greyed out until a course is picked from the list above it) plus a "Browse…" button that still goes through the existing native `dialog.showOpenDialog` path. Dropping a file requires a course first because the modal doesn't know which course a bare file belongs to — selecting one just highlights it and enables the dropzone; nothing uploads until a file actually lands.

**Files dropped can't rely on a real filesystem path.** Electron's exposure of a dropped `File`'s `.path` is deprecated/unavailable under `contextIsolation: true`, so drag-and-drop reads the file's contents via `file.arrayBuffer()` in the renderer and sends the buffer over IPC (`resources:uploadBuffer` → `importBufferIntoCourse()` in `main.ts`) rather than a path `importFileIntoCourse()` could `copy` from. This is the same buffer-over-IPC pattern already used for note images (`notes:saveImage`), just applied to resources.

**Dropping a file directly onto the Resources page list** (not just inside the modal) is also wired up: a drop handler on `#resources-split` uploads immediately to whichever course the rail is currently filtered to, or opens the course-picker modal with the file already attached (skipping its dropzone entirely — the course is the only thing left to choose) if "All Resources" is showing.

### Notes editor: two distinct fullscreen levels

The Notes editor's only "fullscreen" option (from the original reskin) just collapsed the sibling list column so the editor filled the page's own width — it never actually covered the sidebar or top bar, which is what prompted the user to point out it wasn't real fullscreen. Split into two buttons with distinct icons: **"Expand width"** (`#note-widen`, the original behavior, toggles `.pane-fullscreen` on `#notes-split`) and **"Fullscreen"** (`#note-fullscreen`, new — toggles `.true-fullscreen` on `#notes-editor-pane` itself, which pulls it out of the page grid entirely via `position: fixed; inset: 0`, the same mechanism `#preview-overlay.fullscreen` already used for the Resources modal). The "F" keyboard shortcut now triggers genuine fullscreen, matching what F does on the Resources preview.

### Grid/List order and toolbar position standardized between Courses and Resources

Courses' view toggle was already Grid-then-List; Resources' and Deadlines' were List-then-Grid (inherited from before the rename in the previous round) — swapped to match. Resources also gained a sort dropdown (Name/Recently added/Kind/Course) positioned identically to Courses' own sort-plus-view-toggle grouping (`.courses-toolbar-right`, reused directly), rather than the view toggle sitting alone at the top of the list with no equivalent sort control. Courses' own sort dropdown was extended with Deadlines/Notes options now that `dashboard:courseSummaries` already returns `note_count` alongside `resource_count`/`deadline_count`.

### Course detail page: inline Resources/Notes previews, not just a count button

The two "N Resources" / "N Notes" buttons on the course detail page (session 34) were plain buttons that only navigated away to the filtered global page. Reworked into two small widget cards (reusing `.dashboard-widget` styling) showing up to 5 of the course's own most-recent resources/notes inline, each clickable to open directly, with a "View all →" link still available for the full filtered list. The user explicitly left this one to judgment ("if you think the current functionality is enough then okay") rather than asking for it outright — implemented as a genuine but bounded improvement (existing per-course `listResources`/`listNotes` IPC calls, no new backend surface) rather than skipped or over-built.

### Default application menu removed

Electron auto-generates a File/Edit/View/Window/Help menu (Reload, Toggle DevTools, generic Undo/Cut/Copy/Paste, etc.) whenever `Menu.setApplicationMenu()` is never called — this is what the auto-hidden menu bar (Alt to reveal, session 31) was actually showing, and none of it corresponds to a real Atlas feature. Removed entirely via `Menu.setApplicationMenu(null)` in `main.ts`; standard text-field editing (Ctrl+C/X/V/A/Z) is unaffected since Chromium binds those directly to inputs/contenteditable regardless of whether an application menu exists — confirmed via a Playwright check (`Menu.getApplicationMenu()` returns `null`, and Ctrl+A + typing still replaces an input's contents correctly) rather than assumed.

### Open in place, never redirect — Notes editor becomes a global overlay

The user pointed out that clicking a file from Dashboard or a course detail page shouldn't navigate to the Resources/Notes page first — it should open right there. Two different root causes:

`openPreview()` called `showPage('resources')` for no real reason — `#preview-overlay` already renders as a global modal regardless of which page is underneath it, so the navigation was dead leftover code, safely deleted.

`openNoteEditor()`'s `showPage('notes')` call was not dead code, though — `#notes-editor-pane` lived inside `#page-notes`'s own DOM at the time, and a `display:none` ancestor (which is what a hidden `.app-page` is) prevents a `position:fixed` descendant from rendering at all, regardless of the descendant's own positioning. There's no way to make a nested, page-scoped element behave like a real overlay through CSS alone. So the actual fix was architectural: **the Notes editor moved out of the Notes page's DOM into its own global overlay**, `#note-overlay` — a sibling to `#preview-overlay`/`#course-picker-overlay` near the end of `<body>`, exactly the same pattern the Resources preview already used. `#notes-split` is now just the course rail + list, two columns, matching `#resources-split` — there's no third docked-editor column anymore. The "Expand width"/"Fullscreen" distinction from the previous section is unchanged in behavior, just retargeted: `toggleNoteWidth()` toggles a `.wide` class on `#note-overlay` (widens the modal panel, `max-width: 1400px`) and `toggleNoteTrueFullscreen()` toggles `.fullscreen` (the panel grows to cover the viewport, identical mechanism to `#preview-overlay.fullscreen`).

`openDashboardDeadline()` had the same class of bug even though `#deadline-editor-overlay` was already a global overlay — the `showPage('courses')` call before opening it did nothing useful, just navigated away unnecessarily. Removed, but `selectCourse(course)` is still called (without the page switch) since the deadline viewer's "Edit" button reads the module-level `selectedCourse` variable for mention-candidate lookups; the data needs to be correct even when the visible page doesn't change.

### Dashboard right-click: a custom "Go to" menu, not a native one

Left-click on a Dashboard deadline/resource/activity item now always opens it in place (per the above). Right-click adds `#dashboard-goto-menu` — a single "Go to" action that navigates to where the item lives (`showPage('courses')` + `selectCourse()` for a deadline, or `resourcesCourseFilterId`/`notesCourseFilterId` + `showPage()` for a resource/note, reusing exactly the same filtering mechanism the course detail page's own "View all" links already use) **and then also opens/previews the item there** — `openDeadlineViewer()`/`openPreview()`/`openNoteEditor()` fire right after the navigation, so "Go to" reproduces the original pre-session-37 dashboard-click behavior (navigate + open) exactly, just moved from left-click to right-click once left-click became "open in place, don't navigate." This is a small custom-built DOM menu (`showGoToMenu()` in `renderer.ts`), not Electron's native `Menu` API used for resource/note/course right-click actions elsewhere — those exist because deleting a file is something the OS-level menu makes sense for, but "go to" is pure in-renderer navigation with nothing for the main process to do, so a native round-trip would be pure overhead.

### Session 36: smaller polish items

A third, smaller feedback round (5 items) refined details from the previous two rather than adding new structure:

- **Resources list-view row layout**: the kind tag (`.resource-kind` on the third `<span>` in `resourceListItem()`) is pushed to the row's right edge via `margin-left: auto`, instead of sitting immediately after the course name — the row reads name → course (grouped, left) → kind (right).
- **Clickable text now looks like a button.** `.back-link` ("← Back to Courses") and `.link-button` ("View all →") were both bare colored text with an underline-on-hover — restyled to the same bordered/background secondary-button look used elsewhere in the app. Standing convention going forward, logged in Claude's memory: anything clickable in Atlas's UI should default to looking like a button, not plain text.
- **Notes editor icon/meaning mismatch fixed.** "Expand width" (`#note-widen`) and "Fullscreen" (`#note-fullscreen`) had their icons backwards since session 35 — widen was showing the corner-expand glyph that means "fullscreen" everywhere else (`#preview-fullscreen`), and fullscreen was showing an unrelated monitor icon. Swapped: widen now uses a `↔`-style horizontal double-arrow (`NOTE_WIDEN_ICON`/`NOTE_WIDEN_COLLAPSE_ICON`), fullscreen uses the shared corner-expand icon (`NOTE_FULLSCREEN_ICON`/`NOTE_EXIT_FULLSCREEN_ICON`) — the same visual language for "fullscreen" now means the same icon in both Notes and the Resources preview.
- **Course-detail resource previews gained the same right-click "Open in browser" the main Resources list already had** — `#course-detail-resources-preview` items only had a click handler before; added the same `contextmenu` → `atlasApi.showResourceContextMenu()` wiring, no new IPC surface needed since `resources:contextMenu` already existed in `main.ts`.
