# Atlas — Roadmap

This roadmap sequences the project into buildable phases. Nothing here is committed to a calendar date — phases are ordered by dependency, not by deadline, and should be re-scoped as we learn from building each one. This file is meant to be self-contained: everything worth knowing about a feature's status lives directly in its bullet below, not in a separate spec file.

## Phase 0 — Foundation

- [x] Repository created (private, `PamacKR/Atlas`)
- [x] PRD, architecture, roadmap, and behavior documentation
- [x] Project scaffold: Electron + TypeScript app skeleton, SQLite schema v1, build/dev tooling
- [x] Decided and documented the on-disk data directory layout — original files, database, and config all live under `Downloads/Atlas-Storage`, a folder outside this repo so nothing about running/developing the app can ever touch real data through git operations

## Phase 1 — Core data model & local-only workflow

Goal: Atlas is useful *before* any external sync exists.

- [x] Canonical SQLite schema: courses, resources, notes, deadlines, announcements, assignments
- [x] Manual upload (PDF, PPTX, DOCX, images, text, markdown) — file picker, copies into `Downloads/Atlas-Storage/files/<course name>/` (folder named after the course, original filename kept), kind auto-detected from extension
- [x] Resource Viewer: in-app preview for PDF (local `pdfjs-dist` canvas rendering), image, markdown (rendered), text, DOCX (via `mammoth`), and XLSX (via `xlsx`/SheetJS, rendered as HTML tables); PPTX gets a text-only slide outline (no layout fidelity — no good free library renders real slide layout); right-click → "Open in browser" opens the resource in the real OS browser via a local loopback HTTP server, for full-fidelity viewing and fast tab-switching between files
- [x] List/icon view toggle for the resource list, file-manager style
- [x] Local folder watching: explicit per-course folder mapping (`chokidar`), new files copied into the course's managed storage automatically, same as manual upload
- [x] Notes: Markdown, flat per course (session-titled, e.g. "W1L1"), live-rendering WYSIWYG editor (`@milkdown/crepe` — supports live list/heading/divider shortcuts, math via KaTeX, toolbar active-state), autosaved
- [x] Semester filter for the course list, persisted across launches
- [x] Course workspace UI: Overview, Resources, Assignments, Announcements, Notes, Deadlines, Files, Settings — the course detail page is a tabbed layout (Overview/Deadlines/Announcements/Assignments/Classwork/Files) once Classroom sync gave Assignments/Announcements/Classwork real data to show. A real app-wide Settings page also shipped, hosting Drive/Classroom connections plus theme/accent-color.
- [x] Unified Resource Library (single view regardless of source) — manual upload and local folder watching already land in the same per-course resource list/table regardless of source; Classroom/Gmail/Drive sources are Phase 3
- [x] Dashboard v1: upcoming deadlines, recently added resources, "what changed today"
- [x] Global search (SQLite FTS5) across courses, resources, notes

## Phase 2 — Handwritten notes

- [x] Import flow: photos, scans, phone scans, tablet exports — "+ Import scan" on the Notes page, multi-select or drag-and-drop, PDF (multi-page, the primary real-world case — Adobe Scan and similar apps) and single images both supported
- [x] OCR pipeline (local, offline via Tesseract.js), storing both original image and extracted text — one imported file (however many PDF pages) becomes one note. OCR itself is **opt-in per note** (a "Run OCR" button, reviewed before accepting), not automatic on import — the user found local OCR's accuracy on real handwriting too poor to trust silently, and prefers reading a scan via an AI agent's vision when an accurate read is needed.
- [x] Handwritten notes searchable and surfaced identically to typed notes — once OCR is run and accepted (or the user just types over the scan), a note behaves exactly like a typed note (autosave/search/editing, no special-casing); a small ✍️ badge, "View original scan," and "Run OCR" are the only visible differences

## Phase 3 — External sync (current)

Reordered 2026-07-26 (user decision) to build the **Google Drive adapter first**, ahead of Classroom/Gmail — it directly replaces the manual phone-scan/tablet-note transfer workflow, which was the actual immediate pain point.

Reordered again 2026-07-28 (user decision): the two remaining non-Gmail items below (**conflict handling**, then **sync configuration**) came next, then **Phase 4**, and the **Gmail adapter last** — so the actual working order across the two phases was: conflict handling → sync configuration → Phase 4 → Gmail.

**Superseded 2026-07-29:** the Gmail adapter itself was later descoped entirely (see the struck-through item below) — this paragraph is kept as an accurate record of the sequencing decision at the time, not as a live plan.

- [x] Google Drive adapter (first): one Drive folder the user designates as an "inbox" (recursively scanning subfolders too), polled while Atlas is running (~20s) plus a full scan on every launch — not a webhook/push subscription, which would need a public HTTPS endpoint that doesn't fit a local desktop app. New files surface in a review panel (course + Resource/Note per file, individually or in bulk, an explicit Ignore action too, dismissible and reopenable later, not forced immediately). Files are downloaded and copied into local managed storage on import — Drive is the inbox, Atlas still owns the data afterward, same as every other source.
- [x] Google Classroom adapter: a separate OAuth connection from Drive's (college Workspace account), no background polling (launch scan + manual "Sync now" only). New Classroom courses surface in a course-mapping review panel (name-match suggestion, confirm map-to-existing-or-create-new — never auto-assigned); once mapped, coursework/announcements/classwork sync automatically into `assignments`/`announcements`/`classwork_materials`/`resources` (each mapped course guarded by its own try/catch, so one course's sync failure can't silently zero out every other course), and assignments also mirror into the existing `deadlines` Dashboard timeline. Attachments land as Drive-link `resources` (`kind='link'`, opened externally, no download) rather than downloaded files. A per-course "Connect to Classroom" button on course detail lets an already-existing Atlas course link directly to a Classroom course.
- [x] Ashoka Planner course import (local add-on, not an OAuth-based sync source): a user-invoked "Import from Ashoka Planner" button on the Courses page, reading the user's separate `ashoka-planner` app's own SQLite database (read-only, one-shot) for currently-secured courses and creating matching Atlas courses — the intended companion to the Classroom adapter above, so next semester's courses can be pre-created here and then *linked* (not re-created) when Classroom's course-mapping review finds them, or via the per-course Connect button.
- [x] Course-detail Announcements/Assignments/Classwork sections, Dashboard "Upcoming" widget redesign, and a new Calendar page (month grid + Upcoming sidebar, v1 scope — Day/Week toggle, date-picker, and Filters panel are logged fast-follows).
- [x] Office file (PPTX/DOCX/XLSX) preview via Google Drive: "Open in Google Drive" uploads a resource to a dedicated Atlas-managed Drive folder (cached — only the first open of a given file re-uploads) and opens Drive's own real-layout viewer, alongside the existing local text-only preview rather than replacing it.
- [x] **Conflict handling for data that changed both locally and at the source.** Per-field protection: a field the user edited by hand is never overwritten by a re-sync, while fields they didn't touch still accept source updates (deliberately *not* whole-row locking, so a cosmetic title edit can't blind a deadline to a real due-date change). Locally-overridden items get a visible marker plus a "Reset to Classroom version" action; items deleted at the source are greyed out and dismissible via the existing Delete action rather than hard-deleted, since a delete could destroy notes/`@`-mentions attached to them.
- [x] **Sync configuration: manual vs. automatic, frequency.** A Sync section in Settings with per-source **Off / On launch only / Every N minutes**, a "last synced" timestamp and last error per source, and per-source + global "Sync now". Defaults preserve the prior hardcoded behavior exactly (Drive 20s, Classroom launch-only).
- ~~Gmail adapter~~ — **descoped from Atlas entirely (2026-07-29 user decision).** Previously planned as a tracked-sender-list adapter sequenced after Phase 4. The user decided Gmail doesn't belong in Atlas at all — if built, it would be a separate, standalone tool that reads out important emails, unrelated to this project. Nothing Gmail-specific should be built here going forward.

## Phase 4 — Context Builder & AI agent integration

**Moved ahead of the Gmail adapter (2026-07-28 user decision).** The user's primary want from Gmail — surfacing what they missed in a flood of college email — is a Phase 4 capability by definition and can't be delivered by an email adapter alone. Phase 4 is also the product's stated core purpose, and everything already in Atlas (courses, notes, deadlines, resources, Classroom data) is already worth querying — so it delivers value immediately, with or without email.

- [x] Page-aware text extraction: every PDF/PPTX/DOCX/XLSX resource's text is pulled into per-page/slide/sheet/section parts (not filename-only search), extracted on import and backfilled for existing files.
- [x] Persistent agent memory: plain-Markdown files per course + one general file, in `Atlas-Storage/course-profiles/`, read/written directly by the AI agent — not just presentation preferences but familiarity/weak spots, how a course runs, and work already done. Never shown in the Atlas UI or parsed by Atlas itself.
- [x] Agent-generated notes: an agent can create (never edit/overwrite) notes, flagged and badged distinctly from the user's own typed/imported/scanned notes, with a Notes-page filter.
- [x] Context Builder query layer (`src/main/contextBuilder.ts`): plain functions — overview, course briefing, search, list resources/deadlines, read a document page range or a note, write memory, create a note — shared by the MCP server and the static export.
- [x] Local MCP server (`src/main/mcpServer.ts`) exposing all of the above to any MCP-compatible AI agent (Claude Code, Codex, Cursor) over stdio. See `mcp-setup.md` for connecting a tool.
- [x] Static context-file export ("Export for AI" on course detail) as a fallback path for non-MCP AI tools.
- "Fresh conversation" flow (`atlas_overview`) already lets a connected agent pick up full context with no manual explanation — course AI profiles are folded into the memory files above rather than a separate settings form.
- [x] Remote attachment reading: Classroom Drive attachments (and links discovered inside them, e.g. a professor's course-index spreadsheet) are fetched, extracted, and discarded — never downloaded into `Atlas-Storage/files/` — so the agent can read them like any local resource. Required the user to reconnect Google Classroom once for a new Drive scope.

## Phase 5 — Lifecycle & polish

- [x] Course archiving: archive/unarchive a course (right-click or a detail-page button) without deleting anything; a "Show archived courses" toggle on the Courses page shows one list or the other; archived courses stop auto-syncing from Classroom but stay fully searchable.
- [x] Course editing: rename/re-code/re-term a course (right-click on its card, or "Edit course" on its detail page). Only `courses.name/code/term` change — `folder_name` (file storage, Phase 4 memory files) is fixed at creation and never renamed, same tradeoff the storage folder already made.
- [x] Old-course searchability defaults — archived courses stay searchable by default, resolved as part of course archiving above.
- ~~Relationship editing (lecture→course, assignment→lecture, exam→lectures, email→assignment)~~ — **dropped 2026-07-29 (user decision): "i do not see myself using this."** Not deferred; removed from scope. The connections it would have stored by hand are ones a connected AI agent can work out at query time from the actual content, which is the cheaper path and already available.
- ~~Offline-mode audit~~ — **dropped 2026-07-29 (user decision): "95% of the time i will be using this app online."** Atlas already works offline for everything local (the database and files are on disk); this was about auditing and polishing the degraded paths, which isn't worth the effort at that usage split.
- [x] Search dead-click fix: every result type (notes, files, page/slide/sheet hits, announcements, assignments) now opens something when clicked — previously most result types silently did nothing.
- [x] Search ordering: courses first, then file/note names, then in-file content, then Classroom items — hard-partitioned so a strong content match can never outrank a weak name match. Courses are newly searchable at all as part of this — previously typing a course name into search returned nothing unless that text also happened to appear in a file/body.
- [x] **Configurable keyboard shortcuts** — a real shortcut registry (`src/renderer/shortcuts.ts`) replacing the old scattered `keydown` handlers, ~30 actions across navigation/create/search/course-detail-tabs/view-toggles/calendar/preview-and-notes, a `Ctrl+/` cheat-sheet overlay generated straight from the registry (so it can never list a binding that isn't real), and one genuinely global shortcut for quick note capture: `Ctrl+Shift+N`, registered OS-wide via Electron's `globalShortcut` so it works even when Atlas isn't the focused window. A quick-captured note is created **unsorted** (no course assigned) rather than prompting for one first — the whole point is capturing a thought with zero friction — and gets a "Move to course…" action in its editor once the user wants to file it away; the global Notes page shows unsorted notes with an "Unsorted" label rather than hiding them. A new **Settings → Shortcuts** tab lets every binding actually be rebound — click a binding, press the new combo, Esc cancels, a combo already in use asks before reassigning it (which explicitly un-binds the previous owner rather than leaving two actions on the same key) — built now, against the current Settings layout/styling rather than waiting on the Phase 6 redesign, since the user asked for it directly.
- [x] **Empty note discard** — opening "New note" (or quick capture) and closing without ever typing anything, in the title or the body, no longer leaves an empty note behind (empty DB row, empty exported `.md` file, and a stray search-index entry, all silently accumulating). Real content — even just an inserted image with no typed text — still saves normally.

## Phase 6 — Design system, theming & desktop polish

Added 2026-07-29. With the functional product essentially complete, this phase is about Atlas *feeling* like a finished desktop app rather than a working prototype.

- [ ] **Package Atlas as a real Windows app** *(deferred until public release)* — `electron-builder` is configured (`npm run package:win`), and the native PNG/ICO now match the exact supplied logo with transparent backgrounds. The installer output and packaged-app validation remain deferred until public-release preparation. The target is a real NSIS installer with its own `Atlas.exe`, Start Menu entry, and Desktop shortcut, with no build step or console window at launch.
- [x] **Logo and app icon — comparison pass** — cropped transparent versions of the exact dark/light logo images supplied by the user are active in the renderer, taskbar/window icon, and Settings → About, and the native Windows icon pipeline points at the same approved mark. The earlier SVG approximation remains only as a non-active fallback, while the polished preview generated from it is intentionally not integrated. Atlas v1 is retired, so the plain name "Atlas" is free to use. **Small follow-up, not a branding blocker:** the mark currently appears a few pixels too far right in the sidebar; the next alignment pass should mechanically centre the larger mark on the fixed nav-icon rail and align the “Atlas” wordmark with the left edge of the navigation labels, without changing the approved asset.
- [x] **Stop rebuilding the entire search index on every launch** — a cheap row-count check now skips the full search-index rebuild unless something actually changed while the app was closed (previously it deleted and reinserted all 3,000+ indexed rows on every single launch, and once more per course/watched folder on top of that — both fixed).
- [x] **UI overhaul** — the personal-use UI overhaul is complete on `ui-overhaul-v2`, including the shared Direction A tokens, sidebar shell, Dashboard, Courses, Resources, Notes, Calendar, Settings, shared overlays and controls, search results, command palette, and scrollbar/hover corrections. Public-release polish such as empty/first-run states remains intentionally deferred until Atlas is being prepared for wider use. Approved mockups and `DESIGN.md` remain the visual reference for future changes.
- [x] **Scrollbar and Dashboard hover geometry** — diagnosed against the actual Electron-rendered cascade. All Atlas-owned scrollbars now use 6px rounded tracks/thumbs, and Dashboard scroll-list rows use an intentional side inset so their hover backgrounds keep visible padding and rounded corners instead of being clipped by the scroll container. The focused Dashboard verifier inspects the rendered pseudo-elements, hover geometry, and screenshot.
- [x] **Settings redesign** — real sections (Appearance / Shortcuts / Sources / Files & storage / AI agent / About) instead of everything dumped on one or two tabs. The in-app agent/MCP access switch, storage/extraction status, and local backup surfaces are now built on `ui-overhaul-v2`; the personal-use UI overhaul is complete, while public-release polish remains deferred.
- [x] **Design-style themes — cancelled** — additional visual styles such as brutalism and neomorphism are not needed for Atlas's personal-use scope and will not be pursued.
- [x] **Dashboard v2** — unread announcements and new assignments, each with per-item and "mark all" clearing so they can be removed from the dashboard (the user's explicit requirement — a plain unread list with no way to clear it isn't good enough). A one-time migration marks every already-existing announcement/assignment as already read/seen, so the feature doesn't launch to a wall of everything-ever-posted looking "new." It also includes a user-curated important-announcement picker: choosing an existing announcement pins it to Dashboard until explicitly removed there, while keeping it as the same course record rather than making a duplicate. A third widget for "recently synced items" is recommended *against* — it would duplicate the existing "Recently added"/"What changed today" widgets. This is Phase 6, not Phase 5, because the widgets are a new visual surface on the dashboard and should be built once against the redesigned UI rather than twice.
- [x] **Search results overhaul** — page-level hits collapsed under their parent file so 3,000+ indexed pages can't flood the list, source badges (local file vs. Classroom vs. Drive), a course filter dropdown, and visual section headers in the results dropdown marking the four groups the ordering fix already sorts them into (courses/names/content/Classroom — the order is already correct, from Phase 5 above, but there's no visible label separating the groups yet). Same reasoning as Dashboard v2: this is new visual work on an existing screen, built once against the redesigned UI rather than against the current styling and then again.
- [x] **Command palette (`Ctrl+K`)** — jump to any course/note/file or run any action by name ("sync now", "new note", "export for AI", "switch theme"). Reuses the Phase 5 shortcut registry as its list of nameable actions, and doubles as the discovery surface for keyboard shortcuts (a shortcut only helps once memorized; a palette shows every action and its binding). The deterministic local resolver, guided target selection, destructive-action confirmations, keyboard/focus behavior, and light/dark theme support are implemented. Follow-up ideas are recorded separately below rather than added to a new roadmap phase.
- [ ] **Empty and first-run states** *(deferred until public-release preparation)* — currently blank widgets/lists with no guidance when there's nothing to show yet. Add page-specific empty states and a lightweight first-run setup flow when Atlas is being polished for public use.
- [x] **Local backup of `atlas.db`** — scheduled daily/weekly or off, retaining the five most recent copies in `Atlas-Storage/backups/`, with an immediate-backup action in Settings → Storage. Restore is intentionally deferred until it can safely use a controlled app-restart flow.
- [x] **Density setting — cancelled** — adjustable compact/comfortable spacing is not needed for Atlas's personal-use scope and will not be pursued.
- [x] **Per-course readiness view** — the course-detail Readiness tab reports whether Atlas has usable text for the external agent, with readable / needs OCR / pending / failed / other counts and a concise issue list. It covers resources and notes using the existing extraction status, OCR state, and `document_parts` data; scanned PDFs and handwritten scans link to their existing OCR flows, retryable local extraction failures can be retried in place, unsupported file types/external links are identified honestly rather than counted as failures, and actionable issue titles open their resource, link, or note directly as well as the side action. This is technical text availability only, not academic comprehension or reading-progress tracking. A focused `verify:readiness` Electron check covers the dedicated tab, mixed-state UI, themed title interaction, retry action, and hidden empty state.
- [x] **Calendar rework** — rebuilt on the Direction A UI with functional Month/Week/Day views, a mini date-picker for month navigation, and per-kind/per-course filters. The focused Electron Calendar check verifies the views, filters, 42-cell grids, and hidden-state behavior.
- [ ] **Performance and responsiveness pass — next focus** — audit and improve startup, page navigation, creating/updating/deleting local items, note autosave, background sync/extraction, and folder-watcher activity so local actions feel immediate and visible state updates without switching pages or restarting Atlas. The planned order is: (1) establish focused latency and stale-state checks; (2) remove redundant hidden-Dashboard renders, duplicate IPC/database reads, startup work before the first usable frame, and avoidable N+1 queries; (3) replace synchronous full search-index rebuilds with targeted incremental updates and coalesced background indexing; (4) decouple note export, large file work, extraction, and sync from the interaction path; (5) add a small renderer data cache plus explicit mutation/change events so affected lists, dashboard widgets, course detail, and command-palette data refresh immediately; and (6) lazy-load heavy PDF/editor code until those surfaces are opened. Optimistic rows/placeholders may be used only where a safe rollback exists—the SQLite database remains the source of truth. Verification will use focused throwaway-data latency/stale-state checks followed by careful real-data smoke checks, not a broad speculative refactor.
- Reading/coverage tracking (unread/reading/done per resource, so the agent can be asked "what haven't I covered?") — proposed, still awaiting the user's decision on whether to build it.

## Future ideas / backlog (not a roadmap phase)

These are intentionally recorded as ideas, not committed work or a new Phase 7:

- Command Palette follow-up: broader real-use review with long names and large result lists, advanced target expressions such as deadline date/status/course filters, more overlay-stacking combinations, real connected Drive/Classroom testing, and additional aliases based on the user's natural phrasing.
- Accent colour coverage bug: changing the accent currently updates solid boxes and checkbox controls, but some smaller tinted surfaces, subtle highlights, and tiny accent-derived areas still retain the old/default tint. Audit and fix this later during public-release polish.

## Explicitly out of scope for V1

Personal finance, fitness tracking, habit tracking, general life calendar, non-academic task management, mobile app, multi-user collaboration, **Gmail integration of any kind** (2026-07-29 user decision — a separate, standalone tool that reads out important emails is a possible future idea, but explicitly not part of Atlas).

## How to use this roadmap

Each phase should produce something usable on its own — Phase 1 alone is a working local academic workspace with no external dependencies, which de-risks the sync and AI-integration work that follows. Re-order within a phase freely; don't start a later phase before its dependencies are genuinely done.
